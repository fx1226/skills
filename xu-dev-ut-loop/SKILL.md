# xu-dev-ut-loop

基于通过代码审查的版本开展产品黑盒 UT。主 Agent 负责分派、核对版本、转交缺陷和汇总证据。

## 入口

| 时点 | 必须满足的条件 |
| --- | --- |
| 编写正式用例前 | 固定 `codeSnapshot`，核对研发自测、完整 diff 自查和独立代码审查均对应此快照且通过，无未解阻塞 |
| 正式执行前 | 当前用例版本已独立评审并经用户明确确认（门禁 C），实际构建或设备运行版本与已审快照相符 |

缺当前快照的研发自验证据或独立代码审查时，先按 `xu-dev-review-loop` 补齐。各阶段核对角色身份、上下文与适用权限。
已有产物和执行记录可复用，须核对对应版本、实际执行者与交接依据。

## 角色与分派

| 角色 | 逻辑标识 | 职责 | 只读级别 |
| --- | --- | --- | --- |
| 用例作者 Agent | `fr-test-case-author` | 用例设计、覆盖自查、答复与修改 | 不适用 |
| 用例 Reviewer Agent | `fr-test-case-reviewer` | 独立只读评审与复审 | 强制只读 |
| 入口绑定的开发者 | `fr-developer` 或独立审查中的 `developer` | 执行已确认用例、逐例留证、汇总缺陷、复测与 QA 交接 | 按测试授权 |

- 用例作者和用例 Reviewer 使用不同的独立上下文，且独立于主 Agent、原开发者和代码 Reviewer。
- 原开发者在原角色下执行 UT。主会话是入口绑定的开发者时直接执行，外层绑定了开发子 Agent 时续接该开发会话。
- 分派和交接遵循 [分派、只读与台账契约](references/dispatch-and-ledger.md)。
- 首次分派即给出完整任务、版本化输入、权限、交付物和完成条件。
- 角色子 Agent 直接履约，禁止再次委派，主 Agent 负责追加分派。
- Reviewer 默认 `enforced`。缺强只读先报缺口，获用户明确批准后可降级为 `verified-zero-write`。
- 外部人工审查可记录可核对身份和依据。

## 主流程

| 步骤 | 输入与动作 | 完成条件 |
| --- | --- | --- |
| 1. 核对入口 | 核对已审代码快照和角色绑定 | 同一快照的自验与审查均通过，角色可核实 |
| 2. 设计并自查用例 | 按 [用例设计与评审](references/case-design-and-review.md) 设计并建立覆盖映射 | `formal` 用例、格式、需求依据、覆盖自查可供独立评审 |
| 3. 独立评审闭环 | 作者材料交独立 Reviewer，退回后原作者修改再增量复审 | 当前用例版本明确通过，无未解阻塞 |
| 4. 用户确认 | 将用例版本与评审结论交用户 | 当前版本已获明确确认（门禁 C） |
| 5. 整轮执行 | 原开发者核对实际构建，按 [执行与交接](references/execution-and-handoff.md) 完成首轮全部已确认用例 | 本轮逐例落定 `passed`／`failed`／`blocked` 并留证 |
| 6. 缺陷回流与复测 | 批量交给 `xu-dev-review-loop`，用新快照重建并复测 | 每轮结束后再处理本轮缺陷，核对当前构建的结果和必测覆盖 |
| 7. QA 交接 | 按执行与交接参考汇总实测、复测和版本 | 必测项全通过且无未解阻塞时报告研发测试完成可交 QA，否则报告实际状态 |

若上游显式启用 `preDraftCases`，阶段 1 通过后由原作者将 `pre-draft` 对齐最终快照与回归风险，
转为 `formal` 后才可送审。不得提前评审、确认或执行预起草骨架。

固定版本和本轮用例清单，整轮测完才汇总代码缺陷，禁止中途转入修复。首轮跑全套已确认用例。
复测清单覆盖原失败项与核验过的影响面，影响面无法可靠划定时跑全套。执行、结果继承和回流按 [执行与交接](references/execution-and-handoff.md)。

## 异常路由

| 触发条件 | 动作 | 终态／去向 |
| --- | --- | --- |
| 需求、设计或用例实质变化 | 回到相应前置阶段，变更的用例须独立复审并重新确认 | 回到对应阶段 |
| 快照变化 | 核对新快照的自验和审查，重建并复验受影响项 | 回到步骤 1 |
| 构建、设备或关键环境变化 | 核对与已审快照的对应关系，补测或重测受影响项 | 回到步骤 5 |
| 已绑定的角色不可用 | 按原角色交接版本、证据、轮次和未结项 | 核对接手证据后恢复 |
| 用例评审达到默认 3 轮上限仍未通过、连续两轮无进展或依据不明 | 停止，报告轮次、阻塞与缺口 | `WAIT_USER`，用例评审上限可设 1–20，重启不清零 |
| 单轮评审或执行超 20–30 分钟，或连续两轮阻塞未减 | 先汇报进展、已测／待测项和预计耗时 | `WAIT_USER`，决定继续、缩范围或人工接手 |
| 回流达到 `maxDefectCycles` 后仍需继续修复 | 默认上限 2（可设 1–10），报告未解缺陷及复测结果 | `WAIT_USER`，决定继续、缩范围或回设计 |

## 离散终态与交付边界

| 终态 | 使用条件 | 主 Agent 行为 |
| --- | --- | --- |
| `ADVANCE` | 当前入口、产物、隔离和通过条件全部满足 | 进入下一步并输出紧凑状态卡 |
| `WAIT_USER` | 等待门禁、授权、降级批准、超时或熔断决策 | 停下并只询问当前决定 |
| `BLOCKED` | 角色碰撞、入口缺项、环境失效或指纹漂移 | 停止推进，报告缺口，不宣称通过 |

日常切换和交接末尾输出 6–8 行紧凑状态卡；
跨会话交接、调用台账校验或用户明确要求时，才输出稀疏 `flow-ledger` JSON。
格式、字段与边界见 [分派、只读与台账契约](references/dispatch-and-ledger.md)。

文档默认在对话中按选定格式呈现；给出路径本身不等于写入授权，须另行明确授权。
提交、推送、部署、设备改状态和对外发送交接材料均须分别获得授权。
研发交付不等于 QA 通过。
