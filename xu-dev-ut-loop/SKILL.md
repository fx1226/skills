# xu-dev-ut-loop

编排产品黑盒 UT：核对代码审查入口、设计并独立评审用例、用户确认后整轮执行、
必要时集中修复与复测，最后形成 QA 交接。本技能不替代 `xu-dev-review-loop` 的白盒验证。
主 Agent 只编排、核对、转交和整合，不写正式用例、不代评、不代测、不修代码。

## 入口

| 入口项 | 必须满足的条件 |
| --- | --- |
| 固定版本 | 明确 `codeSnapshot`，并记录对应构建产物或设备运行版本 |
| 白盒证据 | 研发自测、diff 自查、独立代码审查通过且无未解阻塞，四项均对应当前快照 |
| 角色隔离 | 可核对各角色身份、上下文、交接台账与只读约束 |
| 正式确认 | 后续执行前须取得用户对当前用例版本的明确确认 |

任一入口条件缺失即停止正式用例设计与评审，先进入 `xu-dev-review-loop` 补齐。
已有产物可复用，但须核对适用版本；恢复执行记录还须核对执行者、交接和运行版本。

## 角色与分派

| 角色 | 逻辑标识 | 职责 | 只读级别 |
| --- | --- | --- | --- |
| 用例作者 Agent | `fr-test-case-author` | 用例设计、覆盖自查、答复与修改，不执行正式用例 | 不适用 |
| 用例 Reviewer Agent | `fr-test-case-reviewer` | 独立只读评审与复审，不改用例或执行 | 强制只读 |
| 测试执行 Agent | `fr-test-executor` | 整轮执行、证据、缺陷复现、复测与 QA 交接 | 不适用 |

- 三角色使用不同的独立上下文，且独立于主 Agent、入口开发与代码 Reviewer。
- 原开发不得改任执行者，原代码 Reviewer 不得改任用例 Reviewer。
- 分派和交接遵循 [分派、只读与台账契约](references/dispatch-and-ledger.md)。
- 首次分派即给出完整任务、版本化输入、权限、交付物和完成条件。
- 角色子 Agent 直接履约，禁止再次委派；主 Agent 负责追加分派。
- Reviewer 默认 `enforced`；缺强只读先报缺口，获用户明确批准后才可降级为 `verified-zero-write`。
- 外部人工审查可记录可核对身份和依据，不虚构 Agent 会话。

## 主流程

| 步骤 | 输入与动作 | 完成条件 |
| --- | --- | --- |
| 1. 核对入口 | 固定快照并核对四项证据和跨角色隔离 | 四项证据同快照，隔离可核实；否则 `BLOCKED` |
| 2. 设计并自查用例 | 按 [用例设计与评审](references/case-design-and-review.md) 设计并建立覆盖映射 | `formal` 用例、格式、需求依据、覆盖自查可供独立评审 |
| 3. 独立评审闭环 | 作者材料交独立 Reviewer；退回后原作者修改再增量复审 | 当前用例版本明确通过，无未解阻塞 |
| 4. 用户确认 | 将当前用例版本与评审结论交用户 | 有可关联当前版本的明确确认，即门禁 C |
| 5. 整轮执行 | 派执行者按 [执行与交接](references/execution-and-handoff.md) 测试 | 每条已确认用例均有 `passed`／`failed`／`blocked` 与证据 |
| 6. 缺陷回流与 QA 交接 | 整轮结束后按需集中修复、复审、复测并汇总 | 必测项全通过才可称研发测试完成可交 QA；否则报告实际状态 |

若上游显式启用 `preDraftCases`，阶段 1 通过后由原作者将 `pre-draft` 对齐最终快照与回归风险，
转为 `formal` 后才可送审。不得提前评审、确认或执行预起草骨架。

**整轮全量执行铁律：固定版本启动 UT 后，必须整轮测完，严禁中途停下 UT 转入修复或补全。**
即使 100 条用例中 75 条失败或受阻，也须继续执行其余可执行用例并逐条留证。
仅当剩余每条用例均客观无法执行，或触发耗时护栏后用户明确指令中止时，才可提前收口。

整轮结束后按四段链批量回流：

1. 执行者提交全部失败用例、受阻项、复现证据和 `fullRoundCompleted: true`；
2. 开发者集中修复并完成白盒自测、diff 自查，输出 `affectedScope`；
3. 代码 Reviewer 增量复审并核验影响面；
4. 执行者在新快照和新构建／设备上复测失败项与影响面；
   未受影响结果仅在记录版本对应与解耦依据后继承，否则重测。

同一快照与构建／设备版本下可引用阶段 4 纯自动化结果并标明范围，
不得替代黑盒必测项或真机／专用设备实测。安全修复与设备改状态须分别授权。

## 异常路由

| 触发条件 | 动作 | 终态／去向 |
| --- | --- | --- |
| 需求、设计或用例实质变化 | 回到相应前置技能；用例须独立复审并重新确认 | 回到步骤 1 或 2 |
| 快照、构建、设备或关键环境变化 | 受影响证据重审重测，旧结果不得直接继承 | 回到步骤 1 |
| 作者或 Reviewer 不可用 | 同角色交接版本、轮次、结论、证据和未结项 | 接手者至少复核未结项与增量 |
| 默认 3 轮评审耗尽、连续两轮无进展或依据不明 | 停止，报告轮次、阻塞与缺口 | `WAIT_USER`；上限可设 1–20，重启不清零 |
| 单轮评审或执行超 20–30 分钟，或连续两轮阻塞未减 | 先汇报进展、已测／待测项和预计耗时 | `WAIT_USER`，决定继续、缩范围或人工接手 |
| 回流超 `maxDefectCycles` | 默认上限 2（可设 1–10），到上限仍有缺陷即停 | `WAIT_USER`，决定继续、缩范围或回设计 |

## 离散终态与交付边界

| 终态 | 使用条件 | 主 Agent 行为 |
| --- | --- | --- |
| `ADVANCE` | 当前入口、产物、隔离和通过条件全部满足 | 进入下一步并输出紧凑状态卡 |
| `WAIT_USER` | 等待门禁、授权、降级批准、超时或熔断决策 | 停下并只询问当前决定 |
| `BLOCKED` | 角色碰撞、入口缺项、环境失效或指纹漂移 | 停止推进，报告缺口，不宣称通过 |

日常切换和交接末尾输出 6–8 行紧凑状态卡；
跨会话交接、调用台账校验或用户明确要求时，才输出稀疏 `flow-ledger` JSON。
格式、字段与边界见 [分派、只读与台账契约](references/dispatch-and-ledger.md)。

文档默认在对话中按选定格式呈现；给出路径本身不等于写入授权，须另行明确授权。
提交、推送、部署、设备改状态和对外发送交接材料均须分别获得授权。
研发交付不等于 QA 通过。
