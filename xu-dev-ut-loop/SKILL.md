# xu-dev-ut-loop

主 Agent 只编排、核对入口／版本／人工确认、转交材料和整合实际输出，不亲自写正式用例、评审用例、执行正式测试或修代码，也不补写角色结论。本技能聚焦产品黑盒验收（FR 验收矩阵、异常与中断恢复、选定公司格式与真机／专用设备实测），与 `xu-dev-review-loop` 的开发者白盒验证分工明确。用例作者 Agent、用例 Reviewer Agent、测试执行 Agent 须为三个不同的独立上下文，且各自独立于主 Agent、入口记录的开发 Agent 和代码 Reviewer Agent；同一 Agent 不得跨角色顺序切换，包括原开发改任测试执行者或原代码 Reviewer 改任用例 Reviewer。作者负责设计、覆盖自查、答复和修改，不执行正式用例；Reviewer 只读评审，不修改用例或执行；执行者执行已批准用例、记录证据和形成执行／QA 交接材料，不设计或修改用例、改预期或修代码。

- **分派。** 分派前按 [分派、只读与台账契约](references/dispatch-and-ledger.md) 以能力模型绑定用例作者 `fr-test-case-author`、用例 Reviewer `fr-test-case-reviewer`、测试执行者 `fr-test-executor`，不绑定特定 Harness。优先使用可用的专用角色；没有可用配置时，可用通用工具创建符合相同权限要求的独立上下文。权限拒绝或用户指定的方式受阻时报告缺口。用例 Reviewer 默认必须使用强只读约束（`enforced`：只读工具、沙箱或隔离只读材料）；无法强禁写时先停下报告只读缺口，禁止用口头“不要写入”替代，仅在用户获知缺口后明确批准降级为 `verified-zero-write` 时，方可采派工前后工作区／VCS 状态指纹核验零写入并如实标注，检出任何非预期写入立即作废结论并报阻塞。执行者在授权的环境和用例范围内操作。首次分派即提交实质任务，以及版本化输入、权限、交付物和完成条件。要求角色子 Agent 直接完成工作，禁止再次委派。宿主支持时关闭其分派权限。额外分派需求交回主 Agent。

- **验收。** 只验收角色直接完成的交付。在 `flow-ledger` 中按所属父会话／Agent 树／运行器记录可核对的稳定 `contextId` 与 `contextScope`，另记实际 `runHandle`／`resumeHandle`、只读模式与证据、权限、交付及版本。仅有任务 ID 时，核对独立上下文创建证据。续接后若句柄变化，沿用原 `contextId`。先取得作者正式用例及覆盖自查，再分派 Reviewer。取得 Reviewer 对当前版本的通过结论并经用户明确确认后，再分派执行者。已有符合门禁的实际产物可核实后沿用。

- **返工。** 优先续接原会话，无法续接时向同角色新的独立上下文移交版本、轮次、结论、证据及未结项。缺陷修复与代码复审经 `xu-dev-review-loop` 交给入口开发和代码 Reviewer。无法满足分派条件、交接材料不足，或用户要求原会话但无法续接时，报告受阻。

1. **核对入口。** 固定明确的代码快照，核实该快照已有研发自测、diff 自查、独立代码审查通过且无未解决的代码审查阻塞项。任一条件缺失时停止正式用例设计及用例评审，说明缺口，进入或建议使用 `xu-dev-review-loop`；可指出资料或环境缺口。核对入口记录及本任务各角色的身份、Agent 会话和交接台账，分派或同身份接替前确认无跨角色碰撞；可核对的外部人工审查记录外部身份和依据，不虚构 Agent 会话。台账显示身份碰撞时禁止分派；信息不足以证明隔离时先询问或报告受阻，不能声称满足严格隔离。**完成条件：** 四项入口证据均对应当前快照，拟分派角色的隔离可由身份和交接证据核实。
2. **设计并自查用例。** 按 [用例设计与评审](references/case-design-and-review.md) 确定用例格式，将用户指定的 Hillstone／Richsun 格式、适用模板及交付载体随任务交给用例作者 Agent。若上游显式开启 `preDraftCases` 并已产出 `testCasesStatus: "pre-draft"` 骨架，须先待步骤 1 入口全部通过，再由原作者对齐最终 `codeSnapshot` 与代码审查暴露的回归风险，转为正式版本（`testCasesStatus: "formal"`）后送审。作者按参考设计用例，逐条核对验收条件的覆盖或不适用依据。**完成条件：** 作者的正式用例版本（`formal`）、所用格式、需求依据及覆盖自查可供独立评审；依据不足的行为保持待确认。
3. **独立评审并闭环。** 将作者材料和同一格式依据交另一独立上下文的只读用例 Reviewer；退回后交作者答复、修改，再交原 Reviewer 增量复审，遵守同一参考的轮次和停止条件。**完成条件：** 独立 Reviewer 对当前用例版本明确通过且无未解阻塞；无独立能力时仅转交已有草案及自查，不宣称通过。
4. **人工确认。** 将评审结论及当前用例版本交用户，取得用户明确人工确认后才正式执行；Agent 评审不代表研发经理或测试经理批准。**完成条件：** 有可关联当前用例版本的明确确认。
5. **执行、缺陷流转与交接。** 确认后派第三个独立上下文的测试执行 Agent 读取 [执行与交接](references/execution-and-handoff.md)，按实际环境和授权在当前固定版本上**完整执行完本轮全部已确认用例**、逐条记录证据并形成交接材料。**铁律：一旦确定版本进入 UT 执行，严禁发现 Bug 或实现遗漏就中途停止 UT 转向修改代码或补齐功能**——即便大面积用例失败或因前置缺失而受阻（例如 100 条中有 75 条不通过或无法测），也必须继续测完其余全部可执行用例、逐条登记 `passed`/`failed`/`blocked` 及原因，待整轮 UT 彻底完成后，再基于汇总的问题清单统一规划批量 Bug 修复或功能补全并触发一次回流。仅当 `codeSnapshot` 与 `buildOrDevice` 完全一致时可引用阶段 4 已核验的纯自动化结果并标注证明范围，不得替代黑盒必测项或设备实测。主 Agent 按参考执行 `maxDefectCycles` 外环熔断与四段 `affectedScope` 缺陷流转并整合实际输出。已有用例评审通过并人工确认后独立调用本技能，也须核对入口及版本并派独立执行者；恢复执行记录还须核对执行者身份、交接和版本。**完成条件：** 当前版本必测项全部通过且无未解阻塞，才能报告研发测试完成可交 QA；否则报告实际状态，由用户决定是否带风险交接。研发交付不等于 QA 通过。

单轮用例评审或本地／设备执行等待预计或实际超过 20–30 分钟，或连续两轮阻塞项未减少时，先向用户汇报进展与预计，再决定继续、缩小范围或人工接手。文档默认在对话中用 Markdown 呈现所选格式并附精简 `flow-ledger` 块；仅当用户给出保存路径并明确授权写入时才落盘，给出路径本身不等于写入授权。提交、推送、部署及设备改状态须分别获得授权。
