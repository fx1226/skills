# 用例设计与评审

## 选择用例格式

优先采用用户指定的 Hillstone 或 Richsun 格式，读取 [公司用例格式](case-formats.md) 对应章节和表格。
用户指定同格式模板时以模板为准；未指定时依次沿用已确认格式、项目模板、通用 Markdown。

公司格式决定章节、字段及顺序，交付载体按用户要求。
获授权制作 Word 时复现对应表格和合并单元格；作者、Reviewer 和执行者沿用同一格式依据。

## 设计与覆盖自查

入口通过后，由用例作者设计正式用例并固定需求、设计、代码审查及用例版本。
上游 `pre-draft` 不得跳过入口送审或执行；原作者须先对齐最终 `codeSnapshot` 与回归风险，
转为 `formal` 后才可送审。

依据优先级：PRD／验收条件 → 确认设计 → 确定的接口和用户可见行为
→ 既有测试约定 → 实现或代码审查揭示的回归风险。
预期必须来自需求或约定，不能用实现反推正确性；依据冲突或缺失时请求澄清。

每条用例应能定位 **用例 ID、关联 FR／验收条件、前置条件、测试数据、步骤、明确预期、优先级／类型**。
公司格式无专栏的信息放在需求—用例映射中。
步骤和数据须可构造，预期须可观察、可判定，覆盖适用的外部行为和副作用。

覆盖正常、边界、异常，以及适用的状态迁移、重复、中断与恢复、兼容性和受影响模块回归。
作者建立需求—用例映射：每条验收条件关联具体用例，或说明有依据的不适用原因。
不明项目标记缺口，不算已覆盖。将映射、用例及待确认项一并送审。

## 独立评审与闭环

用例 Reviewer 使用独立上下文，与主 Agent、用例作者、原开发者和代码 Reviewer 隔离。
Reviewer 遵守 [分派、只读与台账契约](dispatch-and-ledger.md) 的两级只读协议：
默认 `enforced`；缺强只读先报缺口，获用户明确批准后才可降级为 `verified-zero-write`。
只读核对 `formal` 用例、需求和设计依据、覆盖自查与代码快照，不修改用例或执行测试。

逐项检查验收覆盖、用户目标、预期可判定、数据和环境可构造、异常与回归、重复或不可执行用例。
按选定格式核对章节、逐例表格、字段顺序、预期与执行记录的位置。
Reviewer 给出版本、范围、结论和逐项阻塞依据；主 Agent 只转交实际结论，不代评或补写。

退回后主 Agent 转交原作者逐项答复，修改或澄清并标识新版本；
将上轮结论、逐项答复、本轮增量和影响面交回原 Reviewer。
Reviewer 核实每项闭环，并评审增量及影响面；
未变且可证明解耦的部分可继承上轮结论，记录依据。
无法续接时，向同角色新的独立上下文交接以上记录及轮次。
接手者至少复核未结项和增量，不能凭交接自动通过。
无合适角色时停止，不跨角色复用或由主 Agent 兜底。

累计有效独立评审结论，返工换版本仍累计；结论前问答和调用失败不计轮。
默认最多 3 次，用户指定上限优先，须为 1–20 的整数。
单轮预计或实际超 20–30 分钟，或连续两轮阻塞未减少时，先汇报再决定继续、缩范围或人工接手。
达到上限、连续两轮无实质进展、关键依据不明或评审能力不足时停止并报告缺口。
不能换人或重启清零；无独立 Reviewer 时只交草案和自查。

用例预期行为、关键步骤或覆盖范围发生实质变化时，交原作者修改、原 Reviewer 重新评审，
新版本经用户明确确认后由执行者执行；仅改错别字或补执行记录可保留原确认。
需求变化回主流程，设计实质变化回设计评审，再按入口重新固定版本。
