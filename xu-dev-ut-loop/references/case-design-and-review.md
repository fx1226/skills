# 用例设计与评审

## 选择用例格式

优先采用用户指定的 Hillstone 或 Richsun 格式，读取 [公司用例格式](case-formats.md) 中对应的章节和表格。用户为本次交付指定了同一格式的模板时，以该模板为准。未指定公司格式时，依次沿用本任务已确认的格式、明确适用的项目模板、通用 Markdown。

公司格式决定章节、字段及其顺序，交付载体按用户要求。对话或 Markdown 交付也按所选公司格式呈现；获授权制作 Word 时复现对应表格和合并单元格。记录用例版本所用格式，作者、Reviewer 和执行者沿用同一依据。

## 设计与覆盖自查

入口门禁通过后，由用例作者 Agent 设计正式用例并固定需求、设计、代码审查及用例版本。依据优先级：PRD／验收条件 → 人工确认的设计 → 确定的接口和用户可见行为 → 既有测试约定 → 实现或代码审查揭示的回归风险。实现可用于发现风险，但预期必须来自需求或约定，不能用当前实现行为反推正确性。依据冲突或缺失时列出问题并请求澄清，不编造预期。

每条用例应能定位 **用例 ID、关联 FR／验收条件、前置条件、测试数据、步骤、明确预期、优先级／类型**。通用 Markdown 可直接列出这些字段；公司格式按对应字段容纳信息，表中无专栏的信息放在需求—用例映射等配套材料中。步骤和数据须可构造，预期须可观察、可判定；按项目适用检查 CLI 输出及退出状态、前端显示与交互、API 响应及外部可观察副作用。

覆盖正常、边界、异常，以及适用的状态迁移、重复、交互中断与恢复、兼容性和受影响模块回归。作者建立需求—用例映射：每条验收条件关联具体用例，或说明有依据的不适用原因；不明项目标记缺口，不算已覆盖。将映射、用例及待确认项一并送审。

## 独立评审与闭环

用例 Reviewer 使用与主 Agent、入口开发 Agent、代码 Reviewer Agent、用例作者和执行者各自独立的上下文，只读核对固定用例版本、需求和设计依据、覆盖自查与代码快照，不修改用例或执行测试。逐项检查验收覆盖、用户目标、预期可判定、数据和环境可构造、异常与回归、重复或不可执行用例。按选定格式核对章节层级、逐例表格、字段及其顺序、预期与执行记录的位置。Reviewer 给出版本、范围、结论和逐项阻塞依据；主 Agent 只转交实际结论，不能代评或补写结论。

退回后主 Agent 转交原作者逐项答复，修改或澄清并标识新版本；将上轮结论及版本、逐项答复、本轮增量和影响面交回原 Reviewer。OpenCode 分别以原 `fr-test-case-author`、`fr-test-case-reviewer` 的 `sessionID` 续接。Reviewer 核实每项闭环，并评审增量及影响面；未变且可证明解耦的部分可继承上轮结论，记录依据。原作者或 Reviewer 不可用时，只由同身份的独立 Agent 接手并交接以上记录及轮次；OpenCode 接替会话仍须使用对应专用 Agent ID。接手的 Reviewer 至少复核未结项和增量，不能凭交接自动通过。无合适角色时停止，不跨角色复用或由主 Agent 兜底。

累计有效独立评审结论，返工换版本仍累计；正式结论前的问答和调用失败不计轮。默认最多 3 次，用户明确上限优先，须为 1–20 的整数。达到上限仍未通过、连续两轮无实质进展、关键依据不明或独立评审能力不足时停止，报告轮次、阻塞和缺口；不能换人或重启来清零。无独立 Reviewer 时只交草案和自查。

用例预期行为、关键步骤或覆盖范围发生实质变化时，交原作者修改、原 Reviewer 重新独立评审，新版本经用户明确确认后由执行者执行；仅改错别字或补执行记录可保留原确认。需求变化回主流程，设计实质变化回设计评审，再按入口重新固定版本。
