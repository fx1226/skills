# 公司用例格式

以下格式分别依据 Hillstone 的 FR UT-report 和 Richsun 的需求回归测试记录样例。附件作为章节、字段和版式的参考。按当前需求编写内容，以实际执行证据填写结果栏。

## Hillstone

完整 UT 报告按 `Testing Overview（总体测试说明）` → `单元测试环境`
→ 分类测试章节 → `Testing Tips To QA（对QA补充测试建议）` 组织。
总览用 `Item No.`、`Short Description`、`Detail` 三列列出测试范围。
按任务选用 `CLI Testing（命令行测试）`、`Function Testing（软件功能测试）` 等适用类别，
类别下可按子功能分组。完整报告可保留评审人、修订历史、目录和评审纪要；
仅交付用例时从相关测试类别开始。

每条用例以编号标题定位，标题下放一张两列表格，左侧窄列为英文标签，右侧宽列写内容。Markdown 可用以下骨架，Word 表格从 `Summary` 行开始。

| 字段 | 内容 |
| --- | --- |
| Summary | 用一句话说明测试场景或验证点。 |
| Input and Step | 写清初始状态、数据和命令或界面操作，按执行顺序编号。 |
| Expected Result | 与关键步骤对应，写可观察、可判定的预期。 |
| Actual Result | 设计稿留空。执行后填实际观察及证据索引。 |
| Pass and Analyze | 设计稿留空。提交执行记录时填写实测判定及分析，或逐例标明未执行、受阻及原因。 |
| UT Automation | 记录自动化情况。已确定时填写 `YES` 或 `NO`，待确认时留空或标待确认。 |
| Non-Automation Reason | `NO` 时说明具体原因。 |

以用例标题编号关联需求—用例映射，映射中记录验收条件及需要保留的优先级等信息。

## Richsun

完整需求测试记录在正文先交代引言、定义和缩略语、输入文件、人员角色和职责、测试环境、测试技术与测试策略，再进入「测试用例」。按范围选用所需章节。仅交付用例时从「测试用例」开始，按功能模块分组，每条用例用编号小节标题及独立表格。

单张 Word 用例表上半部分填写以下四行。第一至三行为两组「字段、值」，第四行是「前提与约束」及跨剩余列合并的内容区。Markdown 可用以下表格表示该区。

| 字段 | 值 | 字段 | 值 |
| --- | --- | --- | --- |
| 测试用例编号 | 用项目规则生成唯一编号 | 测试用例标题 | 与小节标题对应 |
| 需求编号 | 关联需求编号 | 测试日期 | 设计稿留空，执行后填写 |
| 需求追踪 | 关联具体条款或验收条件 | 优先级 | 按项目定义填写 |
| 前提与约束 | 环境、初始状态、配置及数据准备 | | |

同一 Word 表的下半部分使用以下五列。Markdown 接续五列表呈现。

| 测试目的 | 操作步骤 | 预期结果 | 实际结果 | 备注 |
| --- | --- | --- | --- | --- |
| 说明本用例验证的行为 | 编号写具体操作及输入数据 | 按步骤编号对应可判定的观察项 | 设计稿留空，执行后填实际观察及证据索引 | 提交执行记录时标明状态，按需补充限制、异常或缺陷编号 |

同一用例涉及多步时，在单元格内编号，使关键操作与预期结果可逐项对应。
