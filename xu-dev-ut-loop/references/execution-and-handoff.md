# 执行与交接

## 执行前

主 Agent 核对代码快照、独立代码审查、用例评审及用户确认均适用于当前版本，再按入口身份／会话／交接台账派独立于主 Agent、入口开发 Agent、代码 Reviewer Agent、用例作者和用例 Reviewer 的测试执行 Agent。已有用例评审通过并经用户确认后独立调用本技能也须核对跨阶段身份并派执行者；碰撞禁止分派，无法证明隔离时询问或报告受阻。恢复执行记录时核对原执行者身份、同身份交接台账与构建／运行版本；缺乏对应依据的证据不得视为通过。原执行者不可用时只交接给同身份的独立 Agent，无合适执行者则停止，不由主 Agent 或其他角色兜底。

执行者选择满足验收的实际环境：本地和专用设备不默认互相替代，列出必测项及其环境。版本漂移时由主 Agent 重新核实受影响的审查、确认和证据。

- **本地：** 核对代码快照与构建产物／运行版本的对应关系；命令来自项目文档、脚本或约定。运行前检查脚本及传递调用的副作用、输出位置、共享数据风险和授权。
- **专用设备：** 明确目标和连接、软件或固件版本及其与代码快照的关系、测试数据和前置状态、只读与改状态操作及恢复要求。升级、部署、复位、清数据和重启分别取得授权后操作。无安全自动化通道时给出人工步骤，等待真实结果；给步骤不等于设备通过。

## 结果与失败

**硬性执行原则：固定版本整轮测完，严禁中途中断转入修复。** 一旦锁定当前代码快照与构建／设备版本启动本轮 UT，执行者必须基于当前这版程序**完整执行并判定本轮全部已确认用例**，每条用例均须落定为 `passed`、`failed` 或 `blocked`（附实际证据与归因），不得把其余可执行用例留在 `not-run` 就中止本轮。即使因严重 Bug 或实现遗漏导致大面积失败或受阻（例如 100 条用例中 75 条测不过或因缺失前置能力而受阻），也**禁止**中途停止 UT 流程转向 Bug 修复或功能补全；所有发现的问题统一记录，**必须等本轮 UT 全部执行完毕、产出完整执行结果与汇总缺陷清单后**，再基于完整问题清单一次性规划修复／补全并打包触发 1 次缺陷回流（避免边测边改、反复重建部署或提前耗尽 `maxDefectCycles`）。仅当测试环境／设备彻底瘫痪导致剩余**每一条**用例在客观上均已无法继续执行（仍须逐条登记 `blocked` 与原因，不得借此静默跳跑或直接改代码），或触达 20–30 分钟耗时护栏经用户明确指令中止时，本轮执行才可提前收口。

按已确认用例的格式记录实际结果。Hillstone 和 Richsun 使用 [公司用例格式](case-formats.md) 中对应的执行栏位。每条用例记录执行版本／环境、证据及状态：`passed`（实际符合预期）、`failed`（实际不符合明确预期）、`blocked`（所需条件阻止执行或判定）、`not-run`（尚未执行）。证据记录实际命令或操作、工作目录／环境、版本、预期／实际、退出码或关键结果、可得日志；敏感信息脱敏。分别标注本地模拟、静态推断和设备实测，不扩大其证明范围。仅当 `codeSnapshot` 与 `buildOrDevice` 与 `xu-dev-review-loop` 完全一致时，可引用阶段 4 已核验的纯自动化白盒结果并标明证明范围，不得替代黑盒必测项或真机／专用设备实测。未跑不算通过；环境受阻不直接归因为代码缺陷。本地或专用设备单轮执行等待预计或实际超过 20–30 分钟，或连续两轮阻塞项未减少时，先向用户汇报进展与预计，再决定继续、缩小范围或人工接手。

本轮全部用例执行完毕后，执行者先对汇总问题逐项区分代码缺陷、实现遗漏、用例理解／预期错误、测试数据、环境设备和需求歧义；无法判断时记录待确认及缺失证据。待整轮执行报告汇总后，再对需要代码修复或功能补全的问题**一次性打包**执行 **UT 缺陷回流外环熔断与四段影响面交接链**：

- **外环熔断与内外轮次解耦**：跨阶段缺陷回流上限默认 `maxDefectCycles = 2`（用户可指定 `1–10` 整数），在 `flow-ledger` 的 `loops.defectReturn.cycles` 累计。达到上限后若仍有未闭环缺陷需再次回流，立即停止并向用户汇报缺陷收敛趋势，由用户决定继续、缩小范围或退回设计重评。每次回流进入 `xu-dev-review-loop` 开启独立的增量代码复审周期（默认 `≤3` 轮，计入 `loops.defectReturn.history[n].codeReviewRounds`），不与首次阶段 4 代码审查额度混淆，也不清零历史记录。
- **四段影响面交接链**：
  1. `fr-test-executor` 在**本轮全部用例测完后**提交完整执行结果与汇总缺陷清单（全部 `failedCaseIds`、受阻项、复现步骤、版本与证据，台账记 `fullRoundCompleted: true`）并返回主 Agent；
  2. 主 Agent 基于汇总清单与用户／流程规划修复或功能补全后，交 `fr-developer` 在授权内集中修复、白盒自测、diff 自查，并显式输出 `affectedScope`（改动模块、调用方及建议回归范围）；安全漏洞修复另需明确授权；
  3. `fr-code-reviewer` 在增量复审中核验修复质量与 `affectedScope` 是否遗漏受影响模块／调用方（`reviewerVerifiedScope: true`）；
  4. 复审通过并按影响面重建后，由原 `fr-test-executor`（无法续接时向同执行角色新独立上下文交接）核对新快照与新构建／设备版本，在新产物上复测原失败用例及 `affectedScope` 覆盖用例并更新记录。旧构建、旧代码审查和旧测试证据不能直接证明新快照通过；未受影响的覆盖如需继承，须记录旧证据与新版本的对应关系及解耦依据，证明仍适用，否则重测。执行者不修代码、不设计或修改用例、不改预期；主 Agent 不代修、代审或代测。无法完成必要重审或重测时保持未完成。

执行中若单条用例发现需求歧义或用例预期存疑，先将该条记为受阻／待确认并继续测完其余无歧义用例；整轮结束后若汇总调查使需求、设计或用例发生实质变化，按 [用例设计与评审](case-design-and-review.md) 的变化门禁处理，实质变更的用例在重新独立评审和人工确认前不执行其变更后版本。

## 研发测试文档与 QA 交接

执行者将 QA 交接合并进研发测试文档并返回主 Agent 整合，记录：

- 需求、设计、代码和用例版本，以及构建产物和实际运行版本的对应关系；
- 必测覆盖、逐例状态和证据、缺陷与复测结果；未执行、受阻及未解决事项；
- 环境和设备、部署／配置、测试数据准备和恢复步骤、已知限制及 QA 验证重点。

交付前复核当前版本和证据。必测项全通过且无未解阻塞才报告研发测试完成可交 QA；否则列明实际状态和风险，是否带风险交接由用户决定。无论哪种交接均不代表 QA 已通过或验收。
