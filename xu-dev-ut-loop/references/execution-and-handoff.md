# 执行与交接

## 执行前

主 Agent 核对各产物和确认均适用于当前版本，再按入口身份与交接台账派测试执行者。
执行者须独立于主 Agent、入口开发、代码 Reviewer、用例作者和用例 Reviewer；
独立调用也须核对隔离，碰撞或无法证明时报告受阻。

恢复执行记录时核对原执行者身份、同身份交接台账与构建／运行版本。
缺乏对应依据的证据不得视为通过。
原执行者不可用时只交接给同身份的独立 Agent；无合适执行者则停止，不兜底。

执行者按验收选择环境，列出必测项；本地和专用设备不默认互相替代。
版本漂移时由主 Agent 重新核实受影响的审查、确认和证据。

- **本地：** 核对快照与构建产物／运行版本的对应关系；命令来自项目文档、脚本或约定。
  运行前检查脚本及传递调用的副作用、输出位置、共享数据风险和授权。
- **专用设备：** 明确目标和连接、软件或固件版本及其与快照的关系、测试数据和前置状态。
  升级、部署、复位、清数据和重启分别取得授权后操作。
  无安全自动化通道时给出人工步骤并等待真实结果；给步骤不等于设备通过。

## 结果与失败

**硬性执行原则：固定版本整轮测完，严禁中途中断转入修复。**
锁定版本启动 UT 后，每条已确认用例均须落定为 `passed`、`failed` 或 `blocked` 并留证。
即使 100 条中 75 条失败或受阻，也不得停止 UT 转入修复或功能补全；
不得把其余可执行用例留在 `not-run`。问题汇总后打包触发 1 次缺陷回流。

仅当环境／设备彻底瘫痪导致剩余**每一条**用例均无法执行时，才可提前收口；
仍须逐条登记 `blocked` 与原因，不得借此静默跳跑或直接改代码。
触发 20–30 分钟耗时护栏并经用户明确指令中止时，也可提前收口。

按已确认用例的格式记录实际结果。Hillstone 和 Richsun 使用 [公司用例格式](case-formats.md) 对应栏位。
每条记录执行版本／环境、证据及状态：`passed`、`failed`、`blocked`、`not-run`。
证据记录实际命令或操作、目录／环境、版本、预期／实际、退出码或关键结果、可得日志。
敏感信息脱敏；区分本地模拟、静态推断和设备实测，不扩大证明范围。
未跑不算通过；环境受阻不直接归因为代码缺陷。

仅当 `codeSnapshot` 与 `buildOrDevice` 与 `xu-dev-review-loop` 完全一致时，
可引用阶段 4 已核验的纯自动化白盒结果并标明范围，不得替代黑盒必测项或设备实测。
单轮执行等待预计或实际超 20–30 分钟，或连续两轮阻塞未减少时，先汇报再决定后续。

本轮测完后，执行者先区分代码缺陷、实现遗漏、用例预期错误、测试数据、环境和需求歧义；
无法判断时记录待确认及缺失证据，再一次性打包执行以下回流规则：

- **外环熔断与内外轮次解耦**：默认 `maxDefectCycles = 2`（可设 `1–10`），
  在 `loops.defectReturn.cycles` 累计。达到上限后仍有未闭环缺陷需再次回流时立即停止，
  汇报收敛趋势，由用户决定继续、缩范围或退回设计。
  每次回流的代码复审最多 5 轮，可指定更低上限。到上限仍有阻塞时进入 `WAIT_USER`，停止本次送审。
  将实际复审轮数计入 `history[n].codeReviewRounds`，保留首次阶段 4 与历次回流的记录。
- **四段影响面交接链**：
  1. `fr-test-executor` 在本轮全部用例测完后提交完整结果与汇总缺陷清单，
     包含全部 `failedCaseIds`、受阻项、复现步骤、版本与证据，并记 `fullRoundCompleted: true`；
  2. 按入口绑定的身份回到 `xu-dev-review-loop`。若 UT 主会话原先就是开发者，先用状态卡保留该轮执行快照、结果、证据及执行者，再在原会话恢复开发；若由外层另派开发者，将同一批材料交回原开发会话。原开发者在授权内集中修复，完成白盒自测和 diff 自查，输出 `affectedScope`（改动模块、调用方及建议回归范围）。安全漏洞修复另需明确授权。
  3. 原代码 Reviewer 在增量复审中核验修复及 `affectedScope`。通过后，将新快照、对应的已审 diff、结论及核实的影响面交回 UT，记录 `reviewerVerifiedScope: true`。
  4. 主 Agent 恢复 UT 编排，由原 `fr-test-executor` 核对新快照与重建产物／设备运行版本，
     在新产物上复测原失败用例及 `affectedScope` 覆盖用例并更新记录。
     无法续接时只向同执行角色新独立上下文交接。
     旧证据不能直接证明新快照通过；未受影响覆盖如需继承，须记录版本对应与解耦依据，
     否则重测。执行者不修代码、不修改用例或预期。
     无法完成必要重审或重测时保持未完成。

单条用例发现需求歧义或预期存疑时先记为受阻／待确认，继续测完其余无歧义用例。
整轮后若发生实质变化，按 [用例设计与评审](case-design-and-review.md) 的变化门禁处理；
实质变更的用例在重新评审和确认前不执行其变更后版本。

## 研发测试文档与 QA 交接

执行者将 QA 交接合并进研发测试文档并返回主 Agent 整合，记录：

- 需求、设计、代码和用例版本，以及构建产物和实际运行版本的对应关系；
- 必测覆盖、逐例状态和证据、缺陷与复测结果；未执行、受阻及未解决事项；
- 环境和设备、部署／配置、测试数据准备和恢复步骤、已知限制及 QA 验证重点。

交付前复核当前版本和证据。必测项全通过且无未解阻塞才报告研发测试完成可交 QA；否则列明实际状态和风险，是否带风险交接由用户决定。无论哪种交接均不代表 QA 已通过或验收。
