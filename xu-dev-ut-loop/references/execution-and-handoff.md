# 执行与交接

## 执行前

主 Agent 核对已审快照、用例确认、实际构建与测试授权，按入口绑定由原开发者执行。
原开发者不可续接时按原开发角色交接，记录接手者、版本、证据与未结项。无法核实角色或交接证据时报告受阻。
恢复已有执行记录时核对实际执行者、交接记录和构建／运行版本。

执行者按验收选择环境，列出必测项；本地和专用设备不默认互相替代。
版本漂移时由主 Agent 重新核实受影响的审查、确认和证据。

- **本地：** 核对快照与构建产物／运行版本的对应关系；命令来自项目文档、脚本或约定。
  运行前检查脚本及传递调用的副作用、输出位置、共享数据风险和授权。
- **专用设备：** 明确目标和连接、软件或固件版本及其与快照的关系、测试数据和前置状态。
  升级、部署、复位、清数据和重启分别取得授权后操作。
  无安全自动化通道时给出人工步骤并等待真实结果；给步骤不等于设备通过。

## 结果与失败

**固定构建和本轮用例清单，整轮测完再转入修复。**
首轮清单包含全部已确认用例，复测清单按核验后的影响范围确定。发现失败后继续执行本轮其余可执行用例。
本轮用例逐条落定为 `passed`、`failed` 或 `blocked` 并留证后，才记 `fullRoundCompleted: true`。

环境或设备导致剩余用例均无法执行时，逐条登记 `blocked` 与原因。
触发耗时护栏且用户明确中止时，保留尚未执行的用例为 `not-run`，将本轮记为未完成。

按已确认用例的格式记录实际结果。Hillstone 和 Richsun 使用 [公司用例格式](case-formats.md) 对应栏位。
每条记录执行版本／环境、证据及状态：`passed`、`failed`、`blocked`、`not-run`。
证据记录实际命令或操作、目录／环境、版本、预期／实际、退出码或关键结果、可得日志。
敏感信息脱敏；区分本地模拟、静态推断和设备实测，不扩大证明范围。
未跑不算通过；环境受阻不直接归因为代码缺陷。

同一 `codeSnapshot` 与 `buildOrDevice` 下可引用 `xu-dev-review-loop` 已核验的纯自动化白盒证据并标明范围。
黑盒必测用例和设备实测按各自的执行要求留证。

本轮结束后按问题归因处理。

| 原因 | 去向 |
| --- | --- |
| 已确认的代码缺陷、实现遗漏 | 汇总成一批，转 `xu-dev-review-loop` |
| 用例步骤或预期有误 | 按 [用例设计与评审](case-design-and-review.md) 更新、复审并确认用例 |
| 环境、设备或数据受阻 | 恢复条件后在原已审版本补测，核对实际运行版本 |
| 需求或设计歧义 | 标为受阻，回对应阶段确认 |
| 原因待确认 | 记录缺失证据，保留当前用例状态 |

### 代码缺陷回流与复测

1. 原开发者归档本轮结果，交接代码缺陷对应的 `failedCaseIds`、复现步骤、实际构建版本和证据。代码修复在授权范围内执行，安全漏洞修复另需明确授权。
2. 按 `xu-dev-review-loop` 批量修复、自验和复审，接收已审新快照与 Reviewer 核验过的 `affectedScope`。代码复审轮次按该技能记录。
3. 从新快照重建程序并核对实际运行版本，记录 `retestSnapshot` 和 `retestBuildOrDevice`。复核已确认用例对新快照的适用性，固定失败项与受影响项的复测清单。影响面无法可靠划定时重跑全套。
4. 原开发者在新构建完成本轮复测。继承未受影响项结果时，标明原执行版本和解耦依据，否则重测。发现新缺陷时先完成本轮复测清单，再决定是否开启下一次回流。

`maxDefectCycles` 默认 2（可设 1–10）。需要续接或校验批次时按 [台账契约](dispatch-and-ledger.md) 记录进行中和已完成的批次。
到上限仍需发起新批次时，汇报已修复和未闭环项，等用户决定继续、缩范围或退回设计。

## 研发测试文档与 QA 交接

原开发者将测试证据交主 Agent 汇总进 QA 交接，记录实际执行者以及以下信息。

- 需求、设计、代码和用例版本，以及构建产物和实际运行版本的对应关系；
- 必测覆盖、逐例状态和证据、缺陷与复测结果；未执行、受阻及未解决事项；
- 环境和设备、部署／配置、测试数据准备和恢复步骤、已知限制及 QA 验证重点。

交付前复核当前版本和证据。必测项全通过且无未解阻塞才报告研发测试完成可交 QA；否则列明实际状态和风险，是否带风险交接由用户决定。无论哪种交接均不代表 QA 已通过或验收。
