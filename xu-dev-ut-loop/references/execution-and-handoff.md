# 执行与交接

## 执行前

主 Agent 核对代码快照、独立代码审查、用例评审及用户确认均适用于当前版本，再按入口身份／会话／交接台账派独立于主 Agent、入口开发 Agent、代码 Reviewer Agent、用例作者和用例 Reviewer 的测试执行 Agent。已有用例评审通过并经用户确认后独立调用本技能也须核对跨阶段身份并派执行者；碰撞禁止分派，无法证明隔离时询问或报告受阻。恢复执行记录时核对原执行者身份、同身份交接台账与构建／运行版本；缺乏对应依据的证据不得视为通过。原执行者不可用时只交接给同身份的独立 Agent，无合适执行者则停止，不由主 Agent 或其他角色兜底。

执行者选择满足验收的实际环境：本地和专用设备不默认互相替代，列出必测项及其环境。版本漂移时由主 Agent 重新核实受影响的审查、确认和证据。

- **本地：** 核对代码快照与构建产物／运行版本的对应关系；命令来自项目文档、脚本或约定。运行前检查脚本及传递调用的副作用、输出位置、共享数据风险和授权。
- **专用设备：** 明确目标和连接、软件或固件版本及其与代码快照的关系、测试数据和前置状态、只读与改状态操作及恢复要求。升级、部署、复位、清数据和重启分别取得授权后操作。无安全自动化通道时给出人工步骤，等待真实结果；给步骤不等于设备通过。

## 结果与失败

按已确认用例的格式记录实际结果。Hillstone 和 Richsun 使用 [公司用例格式](case-formats.md) 中对应的执行栏位。每条用例记录执行版本／环境、证据及状态：`passed`（实际符合预期）、`failed`（实际不符合明确预期）、`blocked`（所需条件阻止执行或判定）、`not-run`（尚未执行）。证据记录实际命令或操作、工作目录／环境、版本、预期／实际、退出码或关键结果、可得日志；敏感信息脱敏。分别标注本地模拟、静态推断和设备实测，不扩大其证明范围。未跑不算通过；环境受阻不直接归因为代码缺陷。

执行者先区分代码缺陷、用例理解／预期错误、测试数据、环境设备和需求歧义；无法判断时记录待确认及缺失证据。代码缺陷由执行者记录复现、版本及证据并返回主 Agent，主 Agent 转交 `xu-dev-review-loop` 的原开发 Agent 在授权内修复、自测及 diff 自查，再由原代码 Reviewer 独立增量复审。无法续接时按对应角色交接，核对新上下文的身份、范围和权限。安全漏洞修复另需明确授权。执行者不修代码、不设计或修改用例、不改预期；主 Agent 不代修、代审或代测。

复审后按影响面重建，尽量由原测试执行者核对新构建及运行版本，在新产物上复测原失败及受影响用例并更新记录；无法续接时只向同一执行角色的新独立上下文交接。旧构建、旧代码审查和旧测试证据不能直接证明新快照通过；未受影响的覆盖如需继承，须记录旧证据与新版本的对应关系及解耦依据，证明仍适用，否则重测。无法完成必要重审或重测时保持未完成。

若调查使需求、设计或用例发生变化，按 [用例设计与评审](case-design-and-review.md) 的变化门禁处理；用例实质变更在重新独立评审和人工确认前暂停正式执行。

## 研发测试文档与 QA 交接

执行者将 QA 交接合并进研发测试文档并返回主 Agent 整合，记录：

- 需求、设计、代码和用例版本，以及构建产物和实际运行版本的对应关系；
- 必测覆盖、逐例状态和证据、缺陷与复测结果；未执行、受阻及未解决事项；
- 环境和设备、部署／配置、测试数据准备和恢复步骤、已知限制及 QA 验证重点。

交付前复核当前版本和证据。必测项全通过且无未解阻塞才报告研发测试完成可交 QA；否则列明实际状态和风险，是否带风险交接由用户决定。无论哪种交接均不代表 QA 已通过或验收。
