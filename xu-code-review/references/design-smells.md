# 设计坏味道：启发式，不是硬性违规

继承本机 `code-review` 的 Fowler 坏味道基线。涉及职责、接口、重复或抽象变化时读取；仅在能说明当前变更带来的具体理解、修改或测试成本时提出。

先检查项目约定与设计理由。坏味道名称不能代替论证；以下修复方向是候选方案，不是强制动作。封装、安全边界、适配层、框架契约和性能布局都可能有充分理由。

| 启发式 | 观察信号 | 可考虑的最小方向 |
|---|---|---|
| Mysterious Name | 名称无法表达角色、单位、范围或副作用 | 改为领域名称；难以命名时先澄清职责 |
| Duplicated Code | 多处出现同一业务规则，修改时易分叉 | 在共同语义稳定时复用；相似语法不必强抽象 |
| Feature Envy | 函数主要操作另一对象的数据且暴露其细节 | 将行为移近拥有不变量的数据 |
| Data Clumps | 同组字段／参数多次共同传递并保持同一约束 | 用领域值对象或清晰参数结构表达约束 |
| Primitive Obsession | 字符串／数字承载需要验证的领域概念 | 在确有不变量时引入小类型 |
| Repeated Switches | 同一分类规则在多处重复分派 | 集中映射或分派；适用时用多态 |
| Shotgun Surgery | 一个规则变化迫使多处同步维护 | 聚合共同变化的知识，减少隐性耦合 |
| Divergent Change | 一个模块因多种无关原因反复变化 | 按独立职责拆分，但保留必要凝聚 |
| Speculative Generality | 为未提出也未证实的场景增加钩子、参数和层级 | 缩回当前需求所需接口 |
| Message Chains | 调用者依赖多层对象内部导航 | 让拥有者提供意图明确的操作；流式 API 不自动算问题 |
| Middle Man | 层只转发且无契约、边界或适配价值 | 合并无价值转发；保留有意的隔离层 |
| Refused Bequest | 子类否认父类大部分契约或无法合理替换 | 检查替换性，考虑组合或缩小接口 |

遵守已通过的自动风格检查；有争议但无具体后果的项省略或列为简短非阻塞建议。仅靠坏味道标签不能定级为阻塞缺陷。
