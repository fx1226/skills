# 校准、验证与报告

## 缺陷门槛

进入 findings 前逐项确认：
1. 审查变更时，仅纳入该变更新增、加剧或激活的缺陷。审查指定文件的当前快照时，纳入快照范围内可证实的缺陷，只有历史证据充分时才判断引入时间。
2. 能定位到被审快照的实际路径或节点。变更审查还需说明前后行为差异。
3. 有可达触发条件、预期与实际差异、具体影响，以及证据或可核实推理。
4. 对需求／规范的违反能引用适用来源；通用可靠性问题能落到语言、接口或业务不变量。
5. 达到下述 Confirmed 或 Probable 门槛；关键前提纯属猜测的项留在待确认。

没有价值的机械风格重复、纯审美、变更审查中与改动无关的旧缺陷、无法解释后果的设计偏好，不进入缺陷数量。范围外但重要的风险可单列，不能悄悄改成当前任务。

## 证据状态

- **Confirmed**：目标环境已复现，或源码、调用链及已确认语义足以形成完整因果证明。静态证明不冒充实测。
- **Probable**：故障机制和主要可达路径有证据，但目标运行时、外部系统保证等关键前提尚待确认。明确写出该前提、已有证据及确认方法。
- **待确认／验证缺口**：纯假设、缺失信息、缺工具、未覆盖节点或尚无足够因果证据。不能当成确定缺陷，也不能因缺工具声称代码正确。

置信度与影响独立：影响大不自动增加置信度，未复现不自动否定充分的静态证明。

## 风险级别

| 级别 | 判断标准 | 例示（仍需证据） |
|---|---|---|
| **P0** | 有证据表明正在发生或即将无条件触发的重大系统性损害，需要立即处置 | 广泛不可恢复数据破坏、严重秘密暴露 |
| **P1** | 在现实重要路径上导致严重安全、数据、资金、可用性或核心功能问题，合并／发布前应修复 | 可达越权、重复扣款、常见路径死锁、不兼容写入 |
| **P2** | 有明确条件和实际影响的功能、可靠性或可维护性缺陷，需按项目策略处理 | 边界结果错误、特定失败路径资源泄漏、明确契约违规 |
| **P3** | 影响较小但可证实的局部问题 | 低影响诊断信息错误、局部契约文档误导 |
| **建议** | 非缺陷的设计取舍、可读性或改进选项 | 没有具体错误后果的命名或抽象偏好 |

级别依赖影响、可达性、范围、恢复难度及已有防护，不根据关键词机械定级。“安全”“缺测试”“规范违规”都不天然对应某一级。

明确的硬性项目规则是否阻塞由项目策略决定；风险级别和合并政策分开表达。审查者提供建议，不冒充正式发布授权。

## 验证门槛

运行前确认：
- 检查由当前项目配置／文档定义，或属于行为已知的非执行式解析／静态检查；自制可执行实验另按用户授权和环境边界判断。
- 已读脚本及必要的传递调用、环境配置；默认不安装依赖、不启动需清理的常驻服务、不连接生产或修改共享数据。
- 输出仅在获准的临时／构建位置，或命令已确认无持久修改。会重写源码、锁文件、快照、生成物或 VCS 状态的命令需对应授权。
- 目标是能检出候选缺陷的最轻验证；事先定义真值、失败表现及适用环境。
- 测试失败区分代码缺陷、环境缺失和既有失败；无法区分时不归因给本次改动。
- 保存命令、工作目录、环境要点、退出码和关键结果；明确哪些未运行、为何未运行。

隔离实验可以在获准位置生成临时夹具和产物；清理本次创建且不再需要的文件／进程，保留物说明用途、位置和停止方式。不得清理他人内容。

## 委派契约（仅获授权时）

按当前环境的协作约定选择可用工具；没有工具或权限时继续直接审查。可将 Standards、Spec、Reliability & Safety 分配给独立角色，无 spec 则跳过该角色。

给每个角色：
- 同一目标、端点／内容指纹、完整路径范围和精确差异获取方式。
- 对应规范／需求路径、已知环境限制、风险触发器及只读边界。
- 回报要求：证据快照、已读路径与缺口、候选问题的触发条件／影响／定位／依据、实际验证及失败状态。

不让多个角色写同一目标文件；避免子 Agent 擅自继续委派。主 Agent 核对关键因果证据，解决冲突、去重并校准风险；不能只拼接原始报告。

## 报告契约

遵循用户明确要求的格式；否则使用以下紧凑结构。默认随用户语言，路径、命令和技术标识保留原样。

### 1. 结论与范围
- 结论：发现哪些最高影响问题；无可报告缺陷时写“本次范围内未发现可报告缺陷”，不保证零缺陷。
- 目标、方向、模式、固定端点／本地快照说明，审查日期按需要提供。
- 三轴各给出：有问题／本范围未发现问题／无法完整评估及主要理由。若缺失的项目事实足以改变某项高影响判断，在结论中点明受影响的行为、已知事实和最小补证方式。其余已取证行为仍可独立下结论。

### 2. Findings（跨轴按风险排序）

每个根因只列一次，允许同时标记多个轴。不同触发机制或修复位置造成独立问题时分别报告，避免把无关缺陷捆绑。

```text
F1 [P1] [Reliability & Safety, Spec] 简短且指向行为的标题
位置：path/to/file:起止行，注明新态／旧态；属性、删除节点等用节点／符号定位
证据：Confirmed（静态证明／实测）或 Probable（关键待验证前提）
触发与影响：什么条件下，预期怎样，实际怎样，会造成什么后果
依据：必要的需求／规范来源、调用链、语言语义或验证结果
建议：最小修复方向，以及能检出该问题的验证
```

行号取实际被审快照的最短充分范围；其他上下文放“依据”，不伪装成 diff 修改行。补丁只有相对行号时标明限制。

### 3. 验证与覆盖
- 实际命令与结果，静态推断和实测分开。
- 适用高风险点的证据摘要；路径很多时合并已覆盖低风险项。
- 未读路径、截断／二进制限制、需求缺口、目标工具链不可用和未验证跨层契约明确列出。
- 有外部漂移时说明哪些结论仍有效、哪些需重审。

### 4. 建议与待确认（仅有内容时）
非阻塞建议、待确认前提和范围外重要观察分开列；不混入缺陷计数。末尾可给出按项目策略的合并建议，但不能把审查结论等同于上线批准。

## 停止条件

路径覆盖已交代、主要高影响风险有证据、候选项已校准且必要验证完成或缺口明确后交付。没有新增风险时不持续扩大范围；不为凑数量制造 findings。
