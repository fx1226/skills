# 盛阳研发中心日志

以昨日日志为接续基准，将当日真实进展整理为可直接粘贴到日志表单的六项内容，篇幅和细节密度接近用户历史日志。使用简体中文，保留项目、模块、协议的技术名称。写作示例与来源见 [references/style-examples.md](references/style-examples.md)：首次使用或需要校准措辞时读取；示例仅用于学习风格。

## 汇集当日工作

1. 以用户指定的日志日期为准；未指定时使用用户本地日期，默认 Asia/Shanghai。跨午夜会话按实际工作归属整理，填报时间或文件修改时间不足以单独证明工作发生日期。
2. 先查找并读取昨日日志，包括用户已给的附件、当前对话或可访问记录；休息日无日志时使用最近一个工作日的日志，并核对日期。沿用其项目分组、任务名称和仍有效的本周目标，将昨日工作、遗留问题与明日计划同今天的事实逐项衔接。昨日的计划不等于今天已执行，旧比例和完成状态也不能直接复制。找不到时标明缺少接续基准，再根据现有事实起草。
3. 从当前对话、工作要点和附件提取今日实际进展；需要补足时，通过可用工具读取当日相关工作会话、指定项目记录、提交和测试结果。合并同一任务的多轮讨论、修改和复测，重点保留项目开发、测试结果及影响推进的问题。会议、现场支持等按实际重要性简记；代码上报、Agent 配置、Skill 等工具工作通常合并为一条，不逐个会话展开。工具不可用或记录不全时说明覆盖范围。
4. 本周目标优先取用户确认的本周计划或同一周最近日志；旧日报可用于延续任务和学习措辞，不能证明今天做过同样的工作。缺少本周目标时，可按已明确的项目方向给出“待确认”的候选目标，不能把反推结果当作既定计划。
5. 任务梳理清楚后、日志定稿前，主动向用户集中询问尚未明确的任务完成百分比。列出简短任务名称及昨日比例（如有），让用户可按顺序回复数字，例如：“对接开发、联调测试、管理平台对接，今日累计进度分别是多少？昨日为 99%、95%、85%。”询问的是截至今日的累计完成度，不是今日增加的百分点；需要填写明日目标比例时一并询问。用户已明确提供的当日比例无需重复询问。
6. 收到进度回复后再将明确数字写入正式日志。等待期间可整理其余内容；用户要求先给草稿或暂时无法提供比例时，保留“进度待确认”，不默认沿用昨日数值。其他影响日期归属、关键结果或计划的信息缺口同样简短询问，避免要求用户重复提供已可读取的信息。

## 六项内容与格式

固定按以下顺序输出六个同名标题。每个字段独立从 `1.` 编号；多模块任务使用缩进四空格的 `a.`、`b.`，必要时再用 `i.`、`ii.`。简单事项直接列一行，不为凑层级重复项目名。

| 字段 | 写作要求 |
| --- | --- |
| 本周目标 | 根据项目计划写本周要达成的个人目标，粒度高于当天动作；保留已明确的优先级。目标未调整时保持同周口径一致。 |
| 今日工作内容 | 写当天实际开展的具体内容、当前结果或进展；按项目分组，会议和临时支持可独立列项。明确属于计划外的工作加“（计划外）”；缺少周计划时不自行判定。 |
| 遇到什么问题 | 写影响目标推进的技术、协作或管理问题：具体表现、影响和已知状态。今日已解决的问题也可记录；沿用问题写出具体对象，不只写“继续处理之前的问题”。 |
| 针对问题的解决方案 | 与问题编号对应，可用“问题简述。 --- 已采取的处理、效果或下一步。”有结果写结果，只有思路写“计划／拟／待验证”；暂时无方案时写需要谁提供什么协助或条件。 |
| 明日计划 | 根据本周或下周目标，承接未完成工作和下一步验证，使用“继续、补充、测试、完善”等动作。已知明日休息则顺延至下一工作日，必要时在字段内容中标注“下周计划／节后计划”，字段标题仍为“明日计划”。调休、加班或休息安排以已知信息为准。 |
| 备注 | 仅补充实际影响工作安排或需单独说明的信息，如现场支持、出差、时间安排或补充结论；不重复今日工作。无补充时留空，用户要求非空时填“无”。 |

问题与方案：明确无问题时两栏可写 `1. 今日暂无。`；无新问题但仍有遗留问题时，保留遗留问题及处理状态。素材未提及问题不等于明确无问题，可写 `1. 待确认：当日是否有需记录的问题。`，方案相应标为待补充。

## 措辞与进度

- 以昨日日志和近期同类日志的篇幅为参照，先保留项目主线，再压缩辅助事项。每个开发或测试子项通常一句；问题与方案只保留关键现象、处理和当前状态。构建批次、测试数量、内部验收编号、组件实现和排查过程留在工作记录中，仅在影响理解结论时写入日报。读取材料多不代表正文要长；用户要求详细版时再展开。
- 采用具体、平实的动作短句，如“梳理……逻辑”“撰写……相关代码”“测试、调试……效果”“和……沟通……方案”“补充、完善……文档”。短项通常一行，问题的原因和处理允许稍长；不强设条目数或字数。
- 优先表达“做了什么、做到哪一步”。按证据分别写“完成方案设计”“完成代码修改”“编译通过”“本地测试通过”“设备联调待完成”等；不能由代码变动推断部署、验收或问题已解决。
- 项目开发、测试等任务保留进度百分比，精简正文时也不能省略。今日比例使用 `（进度 X%）`，明日目标使用 `（计划进度 X%）`，其中 X 替换为已确认的对应数值；明日有具体工作安排不代表目标为 100%。尚未确认时按上述询问流程处理，不能仅输出待确认占位便视为定稿。会议、临时支持和合并的工具事项无需硬加比例。
- 百分比只采用用户明确提供或可靠记录确认的数值及其范围，不按投入时间、提交数量或感觉估算，也不因昨日比例自动递增；区分代码、测试和项目总体进度，不能以其中一项代替整体完成度。
- 项目名、版本和模块名以本次资料为准。历史中类似 `Suricate`、设备型号和模块名称的写法不可未经核实迁移到新日志。
- 用自然的中文分号连接并列动作，句末使用中文标点；保留必要的英文标识。避免口号、夸大的价值评价、操作流水账和未经证实的因果结论。

## 交付前核对

核对六项是否齐全、是否已读取并接续昨日日志、当天新增进展是否有依据、篇幅是否接近历史样本、工具工作是否已合并，以及问题方案、明日计划、百分比和日期是否准确。压缩正文时保留有意义的待验证状态。

默认直接给出六项日志正文，不附写作过程、工具调用、证据表或总结性套话。存在缺失信息时，在正文之外加简短“待确认”说明；用户要求核查依据时再列来源。当前会话只覆盖部分工作时，说明“根据当前可见记录整理”，避免声称已经覆盖全天。

写日志不等于发布日志。只有用户另行要求提交表单、发送或保存文件时才执行对应操作；本 skill 不自行安排每日自动运行。
