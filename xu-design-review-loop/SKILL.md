# xu-design-review-loop

依据 PRD、FR 或变更目标完成技术设计与独立评审；也可只做单次只读设计评审。
主 Agent 只编排、转交、核对版本和整理产物，不代写、代审或兜底。
结论仅适用于固定的需求与设计版本。

## 入口

| 模式 | 入口输入 | 执行范围 |
| --- | --- | --- |
| 完整闭环 | 需求基线、项目约定、现状证据与适用版本 | 执行步骤 1–5，形成设计并复审，等待人工确认 |
| 单次只读评审 | 用户提供的设计版本及可取得依据 | 仅派设计 Reviewer，执行步骤 1、3、5 |

需求或设计版本不明时先固定版本；关键歧义无法确认则进入 `BLOCKED`，不把假设写成事实。

## 角色与分派

| 角色 | 逻辑标识 | 职责 | 只读级别 |
| --- | --- | --- | --- |
| 设计作者 Agent | `fr-designer` | 现状取证、设计、自查、逐项答复与修改 | 不适用 |
| 设计 Reviewer Agent | `fr-design-reviewer` | 四视角独立只读评审与复审 | 强制只读 |

- 两角色使用不同的独立上下文，且独立于主 Agent；同一 Agent 不得先后兼任。
- 分派和交接遵循 [分派、只读与台账契约](references/dispatch-and-ledger.md)。
- 首次分派即给出完整任务、版本化输入、权限、交付物和完成条件。
- 角色子 Agent 直接履约，禁止再次委派；主 Agent 负责追加分派。
- Reviewer 默认 `enforced`；缺强只读先报缺口，获用户明确批准后才可降级为 `verified-zero-write`。
- 收到作者设计后派 Reviewer；收到实际答复及增量或无改动说明后再派复审。

## 主流程

| 步骤 | 输入与动作 | 完成条件 |
| --- | --- | --- |
| 1. 固定依据 | 作者记录需求来源、对象版本、项目约定与真实调用链 | 已确认事实、推断和待确认项分开，歧义已解决或明确阻塞 |
| 2. 设计并自查 | 作者按 [设计模板](references/design-template.md) 形成精简 Markdown | 每条 FR／验收条件有承接，接口、状态、影响面和验证方式可据以实现 |
| 3. 独立评审 | 将固定设计、需求、约定与证据交独立 Reviewer | 按 [评审清单](references/review-checklist.md) 覆盖四视角，输出有定位的阻塞、缺口和建议 |
| 4. 答复与复审 | 作者逐项答复、修改或澄清；原 Reviewer 复核闭环与增量 | 阻塞和必需证据缺口关闭；未变且可证明解耦的部分记录继承依据 |
| 5. 停止或交付 | 主 Agent 核对结论、版本和剩余问题 | 交付当前版本的评审通过结论，或明确停止原因 |

单次只读评审仅由 Reviewer 完成步骤 1、3、5；缺依据时报告评审局限，不代写设计。
评审不拆成多个 Reviewer，四视角由同一个 Reviewer 承担。

## 异常路由

| 触发条件 | 动作 | 终态／去向 |
| --- | --- | --- |
| 作者不可用 | 向新设计作者同角色交接需求、已审版本、反馈、答复与未结项 | 不得由 Reviewer 或主 Agent 接任作者 |
| Reviewer 不可用 | 向新 Reviewer 同角色交接完整台账 | 接手者至少复核未结项和增量 |
| 范围或设计整体变化 | 重新全量评审，不沿用局部继承 | 回到步骤 1 |
| 连续两轮同一问题无实质进展，或默认 3 轮耗尽 | 停止，报告版本、轮次、已做检查、阻塞与缺口 | `WAIT_USER`；上限可设 1–20，重启不清零 |
| 单轮预计或实际超 20–30 分钟，或连续两轮阻塞未减 | 先汇报进展与预计 | `WAIT_USER`，决定继续、缩范围或人工接手 |
| 需求或实质设计变化 | 重新确认需求／设计版本及实现授权 | 完整流程回到入口 |

正式结论计一轮，结论前问答、自查和调用失败不计轮；返工换版本仍累计。
澄清成立可关闭问题，无须为了返工而修改正确设计；非阻塞建议未采纳不单独阻止通过。

## 离散终态与交付边界

| 终态 | 使用条件 | 主 Agent 行为 |
| --- | --- | --- |
| `ADVANCE` | 当前版本证据齐全且本步通过 | 进入下一步并输出紧凑状态卡 |
| `WAIT_USER` | 等待人工确认、实现授权、降级批准或停滞决策 | 停下并只询问当前决定 |
| `BLOCKED` | 角色缺失、依据不足、隔离失败或指纹漂移 | 停止推进，报告缺口，不宣称通过 |

完整流程先交付已评审通过的具体设计版本与结论，再进入 `WAIT_USER`。
只有用户明确确认该版本并授予实现授权后，主流程才可编码；
设计前的笼统“直接实现”或“可以修改项目”仅记为实现授权，不是设计确认。

日常切换和交付末尾输出 6–8 行紧凑状态卡；
跨会话交接、调用台账校验或用户明确要求时，才输出稀疏 `flow-ledger` JSON。
格式、字段与边界见 [分派、只读与台账契约](references/dispatch-and-ledger.md)。

默认在对话中输出 Markdown；仅用户给出保存路径并明确授权时才落盘。
提交、部署另需对应授权。
