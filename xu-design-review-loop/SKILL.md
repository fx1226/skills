# xu-design-review-loop

主 Agent 只负责编排、转交需求／设计／答复、核对版本和评审结论、整理实际产物。设计作者 Agent 负责现状取证、设计、自查、逐项答复和修改；独立设计 Reviewer Agent 负责只读评审。每个子 Agent 上下文只承担一个角色。角色不可用时报告受阻，主 Agent 不兜底。结论只对应固定的设计与需求版本。

- **分派。** 分派前按 [分派、只读与台账契约](references/dispatch-and-ledger.md) 以能力模型绑定设计作者 `fr-designer`、设计 Reviewer `fr-design-reviewer`，不绑定特定 Harness。优先使用可用的专用角色；没有可用配置时，可用通用工具创建符合相同权限要求的独立上下文。权限拒绝或用户指定的方式受阻时报告缺口。Reviewer 默认必须使用强只读约束（`enforced`：只读工具、沙箱或隔离只读材料）；无法强禁写时先停下报告只读缺口，禁止用口头“不要写入”替代，仅在用户获知缺口后明确批准降级为 `verified-zero-write` 时，方可采派工前后工作区／VCS 状态指纹核验零写入并如实标注，检出任何非预期写入立即作废结论并报阻塞。首次分派即提交实质任务，以及版本化输入、权限、交付物和完成条件。要求角色子 Agent 直接完成工作，禁止再次委派。宿主支持时关闭其分派权限。额外分派需求交回主 Agent。
- **验收。** 只验收角色直接完成的交付。收到设计后派 Reviewer，收到实际答复及增量或无改动说明后派复审。在 `flow-ledger` 中按所属父会话／Agent 树／运行器记录可核对的稳定 `contextId` 与 `contextScope`，另记实际 `runHandle`／`resumeHandle`、只读模式与证据、交付和版本。仅有任务 ID 时，核对独立上下文创建证据。续接后若句柄变化，沿用原 `contextId`。
- **返工。** 优先续接原会话，无法续接时按步骤 4 向同角色新的独立上下文交接。无法满足分派条件、交接材料不足，或用户要求原会话但无法续接时，报告受阻。

单次只读设计评审只派独立设计 Reviewer，执行步骤 1、3、5。按用户提供的设计版本直接送审。

1. **固定依据。** 作者记录需求来源和版本、审查对象及版本、项目约定，以及判断所需的真实现状证据，包括相关调用链；单次只读评审由 Reviewer 核查可取得的依据。区分已确认需求、推断和待确认问题；关键歧义向用户确认，无法确认时停止正式闭环并报告，不把假设写成事实。单次评审中缺少依据则说明评审局限。
2. **设计并自查。** 作者按 [设计模板](references/design-template.md) 选择适用内容形成精简 Markdown，记录可复核的设计版本。自查完成条件：每项 FR／验收条件都有设计承接；关键接口和状态可据以实现；未决技术选择没有伪装成已决定；受影响模块及验证方式已交代。未满足时补充或列为阻塞，不能送审冒充完成。
3. **独立评审。** 作者自查后，主 Agent 将固定版本、需求、约定和证据交给另一个独立上下文的一个 Reviewer；已有设计的单次评审可无作者直接派 Reviewer。Reviewer 按 [评审清单](references/review-checklist.md) 从需求／项目、软件研发、测试、受影响模块四个视角检查，不直接修改设计；四视角由同一个 Reviewer 承担。输出阻塞项、证据／决策缺口、非阻塞建议及范围外观察；每项给出定位和触发影响或具体缺口，不以审美偏好充当缺陷。无独立 Reviewer 时只转交作者 Agent 实际产出的草案和自查，说明未完成独立评审；作者也不可用时报告受阻，不代写。
4. **答复与复审。** 作者逐项答复意见，修改设计、补证据或澄清分歧，自查增量及影响面。不同返工轮尽量沿用原作者和原 Reviewer；主 Agent 带上上轮结论与已审版本、逐项答复、本轮设计增量及受影响面交回原 Reviewer。Reviewer 先核实每项阻塞与缺口闭环，再审增量及影响。澄清成立可关闭问题，无须为了返工改正确设计；非阻塞建议未采纳不单独阻止通过。未变且可证明解耦的部分可继承，注明依据。原作者不可用时仅向新的设计作者同角色交接需求、已审版本、反馈、答复与未结项台账，不得由 Reviewer 或主 Agent 接任作者。原 Reviewer 不可用时仅向另一独立 Reviewer 同角色交接台账，不得由作者接任；接手者至少复核未结项和增量。范围或设计整体变化时重新全量评审。
5. **停止或交付。** 默认最多 3 次有效独立评审，用户明确指定上限优先（1–20）。Reviewer 给出正式结论计一次，正式结论前的问答、自查和调用失败不计；同一任务跨版本、重启技能均累计。单轮评审预计或实际超过 20–30 分钟，或连续两轮阻塞项未减少时，先向用户汇报进展与预计，再决定继续、缩小范围或人工接手。达到上限仍未通过、同一问题连续两轮无实质进展、关键需求无法确认或独立评审能力不足时停止，报告版本、轮次、已做检查、阻塞和缺口。全部阻塞及必需证据缺口经 Reviewer 关闭后，交付当前版本的 **Agent 设计评审通过**结论；单次只读评审到此交付，完整设计流程进入人工确认。

完整设计流程先交付已经产生且完成独立评审的具体设计版本及评审结论，等待用户明确确认该版本；同时具备实现授权后，主流程才可继续编码。设计形成前对未来实现的概括要求或预授权只记录为实现授权，不能作为设计版本确认；即使同一提示要求“设计后直接实现”，也须等待上述确认。提交、部署另需对应授权。需求变化退回主流程重新确认；实质设计变化须重新独立复审和人工确认。默认在对话中输出 Markdown 与精简 `flow-ledger` 块；仅当用户给出保存路径并明确授权写入时落盘，不自行创建项目文档目录。
