# xu-design-review-loop

作者负责设计和答复，Reviewer 在独立上下文只读评审，结论只对应固定的设计与需求版本。单次只读设计评审直接执行步骤 1、3、5，不启动完整 FR 主流程，不修改设计。

1. **固定依据。** 记录需求来源和版本、审查对象及版本、项目约定，以及判断所需的真实现状证据，包括相关调用链。区分已确认需求、推断和待确认问题；关键歧义向用户确认，无法确认时停止正式闭环并报告，不把假设写成事实。单次评审中缺少依据则说明评审局限。
2. **设计并自查。** 按 [设计模板](references/design-template.md) 选择适用内容形成精简 Markdown，记录可复核的设计版本。自查完成条件：每项 FR／验收条件都有设计承接；关键接口和状态可据以实现；未决技术选择没有伪装成已决定；受影响模块及验证方式已交代。未满足时补充或列为阻塞，不能送审冒充完成。
3. **独立评审。** 作者自查后，将固定版本、需求、约定和证据交给独立上下文的一个 Reviewer；单次评审由当前只读审查者直接执行。Reviewer 按 [评审清单](references/review-checklist.md) 从需求／项目、软件研发、测试、受影响模块四个视角检查，不直接修改设计。输出阻塞项、证据／决策缺口、非阻塞建议及范围外观察；每项给出定位和触发影响或具体缺口，不以审美偏好充当缺陷。无独立 Reviewer 能力时只交草案和作者自查，说明未完成独立评审；作者模拟角色不能替代独立评审。
4. **答复与复审。** 作者逐项答复意见，修改设计、补证据或澄清分歧，自查增量及影响面。带上上轮结论与已审版本、逐项答复、本轮设计增量及受影响面交回同一 Reviewer；先核实每项阻塞与缺口闭环，再审增量及影响。澄清成立可关闭问题，无须为了返工改正确设计；非阻塞建议未采纳不单独阻止通过。未变且可证明解耦的部分可继承，注明依据。原 Reviewer 不可用时交接台账，接手者至少复核未结项和增量；范围或设计整体变化时重新全量评审。
5. **停止或交付。** 默认最多 3 次有效独立评审，用户明确指定上限优先（1–20）。Reviewer 给出正式结论计一次，正式结论前的问答、自查和调用失败不计；同一任务跨版本、重启技能均累计。达到上限仍未通过、同一问题连续两轮无实质进展、关键需求无法确认或独立评审能力不足时停止，报告版本、轮次、已做检查、阻塞和缺口。全部阻塞及必需证据缺口经 Reviewer 关闭后，状态只能是 **“Agent 设计评审通过，等待人工确认”**；不把模拟视角写成项目经理、研发经理或测试经理批准。

先交付已经产生且完成独立评审的具体设计版本及评审结论，等待用户明确确认该版本；同时具备实现授权后，主流程才可继续编码。设计形成前对未来实现的概括要求或预授权只记录为实现授权，不能作为设计版本确认；即使同一提示要求“设计后直接实现”，也须等待上述确认。提交、部署另需对应授权。需求变化退回主流程重新确认；实质设计变化须重新独立复审和人工确认。默认在对话中输出 Markdown；仅当用户给出保存路径并授权写入时落盘，不自行创建项目文档目录。
