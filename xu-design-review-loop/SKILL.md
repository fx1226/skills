# xu-design-review-loop

主 Agent 只负责编排、转交需求／设计／答复、核对版本和评审结论，可整理实际产物，但不撰写或修改设计、不评审，也不冒充任一角色。设计作者 Agent 负责现状取证、设计、自查、逐项答复和修改；设计 Reviewer Agent 在另一个独立上下文只读评审。二者不能是同一会话或同一通用 Agent 切换角色。角色不可用时报告受阻，主 Agent 不兜底。结论只对应固定的设计与需求版本。

在 OpenCode 中，主 Agent 使用 `subagent` 工具，以 `agent` 参数精确分派：设计作者为 `fr-designer`，设计 Reviewer 为 `fr-design-reviewer`；两者 profile 均须为 `subagent` 模式且不再委派。每个子 Agent 首次调用须一次性提供完整角色任务、已有输入材料、交付物和授权；不得先创建或预占 `sessionID` 再补任务，不得以占位、等待、保持会话或无操作为任务内容。启动回执不等于任务结果；每次分派须有实质任务。涉及作者时，取得作者实际设计后才首次分派 Reviewer，取得作者实际答复及设计增量或无改动说明后才派 Reviewer 复审；已有设计的单次只读评审按下述规则执行。保存各自返回的 `sessionID`，返工和复审用对应 ID 与原 `sessionID` 续接；原会话不可用时按步骤 4 同角色交接。不同 ID 不得互换，也不用其他 Agent 替代；指定 ID 缺失或权限受阻时报告对应角色受阻，主 Agent 不兜底。

单次只读设计评审由主 Agent 编排并派独立设计 Reviewer 执行步骤 1、3、5；OpenCode 中只派 `fr-design-reviewer`，无须设计作者，不启动完整 FR 主流程，不修改设计。

1. **固定依据。** 作者记录需求来源和版本、审查对象及版本、项目约定，以及判断所需的真实现状证据，包括相关调用链；单次只读评审由 Reviewer 核查可取得的依据。区分已确认需求、推断和待确认问题；关键歧义向用户确认，无法确认时停止正式闭环并报告，不把假设写成事实。单次评审中缺少依据则说明评审局限。
2. **设计并自查。** 作者按 [设计模板](references/design-template.md) 选择适用内容形成精简 Markdown，记录可复核的设计版本。自查完成条件：每项 FR／验收条件都有设计承接；关键接口和状态可据以实现；未决技术选择没有伪装成已决定；受影响模块及验证方式已交代。未满足时补充或列为阻塞，不能送审冒充完成。
3. **独立评审。** 作者自查后，主 Agent 将固定版本、需求、约定和证据交给另一个独立上下文的一个 Reviewer；已有设计的单次评审可无作者直接派 Reviewer。Reviewer 按 [评审清单](references/review-checklist.md) 从需求／项目、软件研发、测试、受影响模块四个视角检查，不直接修改设计；四视角由同一个 Reviewer 承担。输出阻塞项、证据／决策缺口、非阻塞建议及范围外观察；每项给出定位和触发影响或具体缺口，不以审美偏好充当缺陷。无独立 Reviewer 时只转交作者 Agent 实际产出的草案和自查，说明未完成独立评审；作者也不可用时报告受阻，不代写。
4. **答复与复审。** 作者逐项答复意见，修改设计、补证据或澄清分歧，自查增量及影响面。不同返工轮尽量沿用原作者和原 Reviewer；主 Agent 带上上轮结论与已审版本、逐项答复、本轮设计增量及受影响面交回原 Reviewer。Reviewer 先核实每项阻塞与缺口闭环，再审增量及影响。澄清成立可关闭问题，无须为了返工改正确设计；非阻塞建议未采纳不单独阻止通过。未变且可证明解耦的部分可继承，注明依据。原作者不可用时仅向新的设计作者同角色交接需求、已审版本、反馈、答复与未结项台账，不得由 Reviewer 或主 Agent 接任作者。原 Reviewer 不可用时仅向另一独立 Reviewer 同角色交接台账，不得由作者接任；接手者至少复核未结项和增量。范围或设计整体变化时重新全量评审。
5. **停止或交付。** 默认最多 3 次有效独立评审，用户明确指定上限优先（1–20）。Reviewer 给出正式结论计一次，正式结论前的问答、自查和调用失败不计；同一任务跨版本、重启技能均累计。达到上限仍未通过、同一问题连续两轮无实质进展、关键需求无法确认或独立评审能力不足时停止，报告版本、轮次、已做检查、阻塞和缺口。全部阻塞及必需证据缺口经 Reviewer 关闭后，状态只能是 **“Agent 设计评审通过，等待人工确认”**；不把模拟视角写成项目经理、研发经理或测试经理批准。

先交付已经产生且完成独立评审的具体设计版本及评审结论，等待用户明确确认该版本；同时具备实现授权后，主流程才可继续编码。设计形成前对未来实现的概括要求或预授权只记录为实现授权，不能作为设计版本确认；即使同一提示要求“设计后直接实现”，也须等待上述确认。提交、部署另需对应授权。需求变化退回主流程重新确认；实质设计变化须重新独立复审和人工确认。默认在对话中输出 Markdown；仅当用户给出保存路径并授权写入时落盘，不自行创建项目文档目录。
