# 用例设计与评审

## 设计与覆盖自查

入口门禁通过后才设计正式用例。固定需求、设计、代码审查及用例版本。依据优先级：PRD／验收条件 → 人工确认的设计 → 确定的接口和用户可见行为 → 既有测试约定 → 实现或代码审查揭示的回归风险。实现可用于发现风险，但预期必须来自需求或约定，不能用当前实现行为反推正确性。依据冲突或缺失时列出问题并请求澄清，不编造预期。

每条 Markdown 用例包含：**用例 ID、关联 FR／验收条件、前置条件、测试数据、步骤、明确预期、优先级／类型**。步骤和数据须可构造，预期须可观察、可判定；按项目适用检查 CLI 输出及退出状态、前端显示与交互、API 响应及外部可观察副作用。

覆盖正常、边界、异常，以及适用的状态迁移、重复、交互中断与恢复、兼容性和受影响模块回归。作者建立需求—用例映射：每条验收条件关联具体用例，或说明有依据的不适用原因；不明项目标记缺口，不算已覆盖。将映射、用例及待确认项一并送审。

## 独立评审与闭环

Reviewer 使用与作者独立的上下文，只读核对固定用例版本、需求和设计依据、覆盖自查与代码快照。逐项检查验收覆盖、用户目标、预期可判定、数据和环境可构造、异常与回归、重复或不可执行用例。Reviewer 给出版本、范围、结论和逐项阻塞依据；作者不能替 Reviewer 宣布通过。

退回后作者逐项答复，修改或澄清并标识新版本；将上轮结论及版本、逐项答复、本轮增量和影响面交回同一 Reviewer。Reviewer 核实每项闭环，并评审增量及影响面；未变且可证明解耦的部分可继承上轮结论，记录依据。原 Reviewer 不可用时，交接以上记录，由接手的独立 Reviewer 至少复核未结项和增量；不能凭交接自动通过。

累计有效独立评审结论，返工换版本仍累计；正式结论前的问答和调用失败不计轮。默认最多 3 次，用户明确上限优先，须为 1–20 的整数。达到上限仍未通过、连续两轮无实质进展、关键依据不明或独立评审能力不足时停止，报告轮次、阻塞和缺口；不能换人或重启来清零。无独立 Reviewer 时只交草案和自查。

用例预期行为、关键步骤或覆盖范围发生实质变化时，新版本须重新独立评审并经用户明确确认后执行；仅改错别字或补执行记录可保留原确认。需求变化回主流程，设计实质变化回设计评审，再按入口重新固定版本。
