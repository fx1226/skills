# xu-dev-test-loop

作者负责用例、自查和执行；独立上下文的 Reviewer 只读评审用例。所有结论绑定具体版本，用户的确认不等于授权提交、推送、部署或设备改状态。

1. **核对入口。** 固定明确的代码快照，核实该快照已有研发自测、diff 自查、独立代码审查通过且无未解决的代码审查阻塞项。任一条件缺失时停止正式用例设计及用例评审，说明缺口，进入或建议使用 `xu-dev-review-loop`；可指出资料或环境缺口。**完成条件：** 四项入口证据均对应当前快照。
2. **设计并自查用例。** 读取 [用例设计与评审](references/case-design-and-review.md)，按需求与约定设计 Markdown 用例，逐条核对验收条件的覆盖或不适用依据。**完成条件：** 用例版本、需求依据及覆盖自查可供独立评审；依据不足的行为保持待确认。
3. **独立评审并闭环。** 按同一参考提交独立只读 Reviewer，退回后答复并由同一 Reviewer 增量复审，遵守轮次和停止条件。**完成条件：** 独立 Reviewer 对当前用例版本明确通过且无未解阻塞；无独立能力时仅交草案及自查，不宣称通过。
4. **人工确认。** 将评审结论及当前用例版本交用户，取得用户明确人工确认后才正式执行；Agent 评审不代表研发经理或测试经理批准。**完成条件：** 有可关联当前用例版本的明确确认。
5. **执行、修复与交接。** 读取 [执行与交接](references/execution-and-handoff.md)，按实际环境和授权执行并记录逐例证据，处理失败与版本变化，整理合并 QA 交接的研发测试文档。**完成条件：** 当前版本必测项全部通过且无未解阻塞，才能报告研发测试完成可交 QA；否则报告实际状态，由用户决定是否带风险交接。研发交付不等于 QA 通过。

文档默认在对话中输出 Markdown；仅当用户给出保存路径并明确授权写入时才落盘，给出路径本身不等于写入授权。提交、推送、部署及设备改状态须分别获得授权。
