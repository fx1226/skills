# 程序门禁调用契约（可选硬计轮路径）

用户明确要求程序强制计轮或判定通过时，按本契约调用兼容的 `workflow` 工具执行现有脚本。它只是可选路径：默认主流程由主 Agent 编排，固定同一审查者做增量复审。门禁每轮新建审查上下文、按全量审查，不能继承固定审查者的增量结论，因此只在需要硬计轮或无人值守判定时使用。

`workflow.js` 不是独立 Node 命令；先定位到目标工作目录，脚本不自行切换目录、执行外部验证命令或改动工作区。

```js
workflow({
  meta: {
    name: "xu-delivery-loop",
    description: goal,
    phases: [{ title: "验证与修复" }, { title: "独立审查" }]
  },
  args: { goal, scope, checks, maxRounds, notes },
  script: /* ../workflow.js 原文 */
});
```

- `scope` 写对象、定位方法、纳入与排除的范围（含暂缓项），以及两侧如何独立生成同一格式的版本标识，不限 Git。`notes` 写授权与限制。
- `checks` 是非空必验清单，每项 `{ id, check, pass }`：唯一 ID、验证方式、通过条件，不要求每项都是命令。涉及构建产物时，在通过条件中写明功能测试须使用与送审快照对应的构建产物；脚本只校验证据条目与版本标识，构建顺序和产物对应关系由审查核实。
- `maxRounds` 省略为 3；显式输入须为 1–20 的整数。可用的后台执行和取回结果方式以该工具为准，启动任务不算完成。
- 返工轮会把上一轮审查结论（阻塞项、证据缺口、快照）交给下一轮审查者做闭环核对；下一轮仍是独立新上下文，按全量复核，不继承上一轮的增量结论，也不得把上一轮结论直接当作本轮通过依据。
- 程序强制检查条目是否齐全、送审对象标识是否一致、审查结论是否有效及轮次上限；实际证据是否可信由独立审查核实。审查只读权限仍须由运行环境约束，不能把提示词当作权限隔离。
- 门禁不执行单轮成本检查点；需要时间护栏时由主 Agent 在主流程中执行。同一阻塞项连续两轮无实质进展的停止线也由主 Agent 依台账判断，门禁只按轮次上限停止。
- 自测失败或证据不能绑定送审对象时，脚本返回 `blocked` 并结束本次运行。重启是新的运行，已用轮次不会自动清零，主 Agent 须把已计有效轮次带入下一次的上限计算。

| `status` | 处理 |
|---|---|
| `approved` | `lastSubmission` 有逐项证据与对象；结合 `summary`、`nonBlocking` 交付，先按主流程复核漂移。 |
| `stopped` | 到有效送审上限，分别列出 `residual` 的阻塞项、`gaps` 的具体证据缺口和非阻塞项；不提交。 |
| `blocked` | 报告理由、已有证据与不完整项，或验证与审查对象不一致；如有价值，可独立做不计轮的部分只读审查。 |
| `dev-failed` / `review-failed` | 未取得有效执行／审查结果，属于流程故障；保留已经取得的证据和返工缺口。 |
| `bad-args` | 先修正调用契约。 |

`round` 永远是已完成的有效送审次数。本次在执行或审查环节出错时，未完成的拟送审轮次是 `round + 1`。不要自动重开脚本清零已用轮次。

维护时从仓库根目录运行 `node --test xu-delivery-loop/workflow.test.cjs`。这只验证脚本判定，不替代兼容运行器实跑；会话路径按 [行为用例](../test-prompts.json) 验证。
