# 程序门禁调用契约（可选硬计轮路径）

用户明确要求程序强制计轮或判定通过时，按本契约调用兼容的 `workflow` 工具执行现有脚本。它只是可选路径：默认主流程由主 Agent 编排，固定同一审查者做增量复审。主 Agent 只编排，不兼任开发或审查；门禁通过开发和审查两个独立调用执行，同一 Agent 不得跨角色，缺角色时报告受阻。门禁每轮新建审查上下文、按全量审查，不能继承固定审查者的增量结论，因此只在需要硬计轮或无人值守判定时使用。

默认使用当前 Harness 的子 Agent 工具按主流程分派开发和代码 Reviewer。可选 `workflow` 仅用于兼容运行器。运行器须把每次调用绑定到对应逻辑角色，提供独立上下文及开发和只读审查所需权限，分别核对角色上下文身份与运行句柄。运行器须关闭角色子 Agent 的分派权限，或在向脚本交付结果前检查该角色的实际调用轨迹，并拒收有再委派的交付。权限、独立性或直接履约无法证明时报告受阻。用户要求程序强制计轮且无兼容运行器时，取得用户同意后才可改走手动路径。

手动路径返工优先交回原开发 Agent；硬门禁每轮调用不能恢复原开发会话，返工由同一开发角色的接手 Agent 根据上一轮送审和审查台账继续，不等于原会话。用户要求原开发会话连续性时，不能用此路径冒充，应报告该路径受阻。

`workflow.js` 不是独立 Node 命令；先定位到目标工作目录，脚本不自行切换目录、执行外部验证命令或改动工作区。

```js
workflow({
  meta: {
    name: "xu-dev-review-loop",
    description: goal,
    phases: [{ title: "验证与修复" }, { title: "独立审查" }]
  },
  args: { goal, scope, checks, maxRounds, notes, devHandoff },
  script: /* ../workflow.js 原文 */
});
```

- `scope` 写对象、定位方法、纳入与排除的范围（含暂缓项），以及两侧如何独立生成同一格式的版本标识，不限 Git。`notes` 写授权与限制。
- `devHandoff` 是可选字符串，默认空，仅用于同一任务首次运行 workflow 前已有开发 Agent 及实现成果时的同角色交接；写明原开发身份或会话（如有）、基线与实现快照、已有 diff 和证据、未结项。FR 主流程已有开发 Agent 完成实现后，首次硬门禁必须由调用方提供该台账；无法提供时不得声称满足角色连续性，应报告受阻，或经用户同意走手动路径。不得用 `devHandoff` 恢复此前 workflow 失败后的同一任务，跨运行仍按下述受阻或手动路径处理。
- `checks` 是非空必验清单，每项 `{ id, check, pass }`：唯一 ID、验证方式、通过条件，不要求每项都是命令。涉及构建产物时，在通过条件中写明功能测试须使用与送审快照对应的构建产物；脚本只校验证据条目与版本标识，构建顺序和产物对应关系由审查核实。
- `maxRounds` 省略为 3；显式输入须为 1–20 的整数。可用的后台执行和取回结果方式以该工具为准，启动任务不算完成。
- 开发侧返回的 `roleHandoff` 为非空字符串：无前序开发时记录无前序交接；首次门禁有 `devHandoff` 或门禁内返工时，如实记录接手及实际收到的版本、已有证据、未结项和继续方式；缺失或空白时返回 `dev-failed`，不送审。Reviewer 收到原始 `devHandoff`（如有）及返工轮的前次开发送审材料和审查结论，对照核实交接内容的真实性和完整性；脚本只校验非空，字段存在不是机器证明。`selfReview` 记录自查范围与结论。必验项通过但该记录缺失时，返回 `dev-failed`，尚未送审。开发者在 `summary` 中逐项回应收到的意见，可引用同一快照的既有依据澄清。审查者核实后可以直接批准该版本，非阻塞意见可随批准保留。
- 返工轮会把上一轮审查结论（阻塞项、证据缺口、快照）交给下一轮审查者做闭环核对；下一轮仍是独立新上下文，按全量复核，不继承上一轮的增量结论，也不得把上一轮结论直接当作本轮通过依据。
- 程序强制检查条目是否齐全、送审对象标识是否一致、审查结论是否有效及轮次上限；实际证据是否可信由独立审查核实。审查只读权限默认须由运行环境强约束（`enforced`），不能把提示词当作权限隔离；若缺少强只读，须先报告缺口并仅在用户明确批准降级为 `verified-zero-write` 后，由主 Agent 在运行前后采集可核验的工作区／VCS 状态指纹确认零写入，检出写入立即作废并报阻塞。
- 门禁不执行单轮成本检查点；需要时间护栏时由主 Agent 在主流程中执行。同一阻塞项连续两轮无实质进展的停止线也由主 Agent 依台账判断，门禁只按轮次上限停止。
- 自测失败或证据不能绑定送审对象时，脚本返回 `blocked` 并结束本次运行。`blocked`、`dev-failed` 或 `review-failed` 后，不支持用新 workflow 运行续接同一任务，不得重启脚本冒充同一闭环或从首轮继续。需要继续时，主 Agent 携带前次输出的版本、证据、反馈、已计有效轮次和角色交接台账，按手动路径角色契约续接；无法完整交接则报告受阻。轮次仍累计，不得借新运行清零。用户仍要求程序强制计轮或判定而未同意手动路径时，报告受阻，不静默降级。

| `status` | 处理 |
|---|---|
| `approved` | 脚本已校验送审材料和评审结论。交付前核对运行器的角色隔离、权限和直接履约证据，并按主流程复核版本漂移。条件满足后结合 `lastSubmission`、`summary`、`nonBlocking` 报告通过。 |
| `stopped` | 到有效送审上限，分别列出 `residual` 的阻塞项、`gaps` 的具体证据缺口和非阻塞项；不提交。 |
| `blocked` | 报告理由、已有证据与不完整项，或验证与审查对象不一致；如有价值，可独立做不计轮的部分只读审查。 |
| `dev-failed` / `review-failed` | 未取得有效执行／审查结果，属于流程故障；保留已经取得的证据和返工缺口。 |
| `bad-args` | 先修正调用契约。 |

`round` 永远是已完成的有效送审次数。本次在执行或审查环节出错时，未完成的拟送审轮次是 `round + 1`。

维护时从仓库根目录运行 `node --test xu-dev-review-loop/workflow.test.cjs`。这只验证脚本判定，不替代兼容运行器实跑；会话路径按 [行为用例](../test-prompts.json) 验证。
