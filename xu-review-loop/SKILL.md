# xu-review-loop

**开发角色构建、自测；独立审查 Agent 只读复核；两边都通过才可提交。** 开发角色可由主 Agent 直接承担；审查必须换上下文独立进行，不能自审；开发子 Agent 只在并行或隔离需要时派。

1. **构建。** 基于最新代码构建。构建输入不变则复用产物与证据，变了才重建。功能测试必须跑在与送审快照对应的产物上。
2. **功能测试。** 范围按需求、项目文档和现有脚本确定，优先复用同一快照可复现的 CI/脚本结果；有副作用的操作先核对并按授权执行。逐项记录通过/失败/受阻、对应版本、实际方法、环境和结果。测试不过先定位修复，修复后按影响面重建、重测。
3. **送审。** 材料写清四件事：新增还是修 Bug、处理逻辑为什么这样改、测试覆盖到哪里、逐项证据（命令/环境/结果/版本）。材料写不清或测试不足，审查可退回。
4. **独立审查。** 首轮做全量只读复核，按 `xu-code-review`，不改代码；只返回通过/退回、阻塞项和证据缺口。返工轮交回**同一审查 Agent**，主 Agent 附审查台账（上轮结论与阻塞项、已审范围、继承项依据）、本轮 diff、受影响面和新增证据；只审上轮阻塞项闭环、本轮增量与受影响面。未改动且可证明解耦的部分继承上轮结论并标注依据，无法证明解耦就重审。同一对象不换审查 Agent；不可用时交接台账，新审查者至少重核闭环与增量；范围或设计级改动作全量审查。范围外历史问题只作观察，不计阻塞。
5. **返工。** 把具体阻塞项和证据缺口交回开发角色：该改代码就改，只缺证据就补证据或补测试。改码后按影响面重建、复测；旧结论只对旧快照有效，下一轮继续用同一审查 Agent 的台账。
6. **通过或停止。**
   - **通过**：全部必验项有对应当前送审版本的通过证据、独立审查确认充分、无未解决的阻塞项。报告本轮可提交；提交是单独动作，按授权执行。
   - **停止**：达到有效送审上限（默认 3 次，用户明确上限优先，1–20）；同一阻塞项连续两轮无实质进展；环境或权限受阻。
   - 轮次只计同一对象的有效审查结论，自测失败或调用失败不计。
   - 单轮预计或实际超过 20–30 分钟，或连续两轮没减少阻塞项时，先向用户汇报进展与预计，再决定继续、缩小范围或人工接手。

交付时说清结论对应的版本、有效轮次、实际测试与审查范围、继承项及依据、阻塞与残留问题。**通过不等于授权提交或部署。**

**边界。** 无需构建的对象（文档、配置、脚本、补丁、已有运行版本）跳过构建，直接对同一可复核版本验证和送审；版本标识与取证按 `xu-code-review`（Git、SVN、文件/补丁各按其方法），两侧独立生成同一格式标识。没有独立审查能力时只交付已有证据，不宣称通过。用户明确要求程序强制计轮或判定时，按[程序门禁](references/workflow.md)执行；门禁每轮新建审查上下文、按全量审查，不能继承固定审查者的增量结论；无法满足时报告受阻。
