# xu-review-loop

**开发 Agent 构建、自测；审查 Agent 独立复核；测试与审查都通过才提交。** 主 Agent 组织闭环、派发和计轮；开发 Agent 负责构建、功能测试和修复，审查 Agent 用独立上下文只读复核，不改代码。流程不绑定版本控制类型，Git、SVN 或其他可复核对象都走同一个闭环。

1. **构建。** 代码编写或修改基本完成后，基于最新代码构建。每次改码后都重新构建；上一次的构建产物、测试结果和审查结论同时作废。
2. **功能测试。** 在本次构建产物上运行功能测试和相关回归，确认实际运行的是本次构建的版本。验证范围按需求、项目文档和现有脚本确定；有副作用的操作先核对并按授权执行；只有验收依据或授权仍不明确时才询问。用户明确暂缓的项列在本轮之外，未获授权或环境不具备的必验项记为受阻。测试不通过：定位问题、修复代码，回到第 1 步。
3. **送审说明。** 测试通过后，按三要素写清：本次是新增功能还是修 Bug；处理逻辑为什么这样改；做了哪些测试、覆盖到哪里。
4. **独立审查。** 审查 Agent 只按送审材料和代码下判断，不改代码。按 `xu-code-review` 核对同一版本，回答通过还是退回，并给出阻塞项和证据缺口；说明写不清或测试不足时退回补充。异步派发以完成通知为准，启动回执不算结果；只证明链路一层的证据不外推。
5. **返工。** 审查退回时，把具体问题和证据缺口交回开发 Agent：该改代码就改，只缺证据就补证据或补测试。改码后回到第 1 步，用新构建产物重新测试、重新送审；旧版本的结论不适用于新版本。
6. **通过或停止。** 测试与审查都通过，报告本轮可以提交，提交由开发 Agent 执行并需单独授权。轮次按送审计：只计同一版本的有效审查结论，自测失败或调用失败不计；默认第 10 次送审仍不通过就停止（用户明确上限优先，1–20 次），同一问题连续修复 3 次仍不过也作为卡点停止；环境或权限受阻时同样停止，并说明继续所需条件。停止时说明原因，并列出还残留哪些问题。

交付时说清结论对应的版本、已用有效轮次、实际测试和审查的范围、阻塞项与残留问题。**通过不等于授权提交或部署。**

**适用边界。** 无需构建的对象（文档、配置、脚本、补丁、已有运行版本等）跳过第 1 步，直接对同一可复核版本验证和送审；对象可以是一次改动、已有改动、运行版本、脚本或补丁，不要求是 Git 仓库；Git 项目用提交或工作区内容指纹标识版本，SVN 项目用修订号与工作副本状态标识版本，文件或补丁用内容指纹，两侧独立生成同一格式的标识，定位与取证按 `xu-code-review` 的固定范围与证据规则执行；已有改动可直接验证，不要求重新实现。没有独立审查能力时只交付已有证据，不宣称通过。用户明确要求程序强制计轮或判定是否通过时，按[程序门禁](references/workflow.md)执行；无法满足则报告受阻。
