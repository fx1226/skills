# xu-fr-flow

用户显式调用本技能后，主 Agent 按档位编排从需求到 QA 交接的完整流程。
主 Agent 只调度、核对和汇报，不代替专业角色产出方案、代码、用例、评审或测试结论。
缺角色、证据或权限时停止对应阶段并报告缺口，不兜底冒充完成。

## 入口与档位

| 档位 | 使用条件 | 流程范围 |
| --- | --- | --- |
| `standard`（默认） | 未显式指定 `lite`，或触发任一升级红线 | 7 阶段、7 角色，门禁 A／B／C |
| `lite`（显式启用） | 用户明确要求 `lite`，且全部红线为否 | 保留阶段 1，合并门禁 AB，再执行阶段 3–7 |

任一红线为真即禁止 `lite` 并升级 `standard`：

1. 跨模块公共接口、协议、数据结构或存储格式变更；
2. 安全或权限边界变更；
3. 专用设备刷写或持久化状态变更；
4. 重大架构或迁移取舍；
5. 未消除的关键需求歧义。

无需正式黑盒 UT 的微型改动直接使用 `xu-dev-review-loop`，不启动本流程。
已有产物或确认记录可复用，但须核对适用版本，从最早未完成或失效阶段恢复。

## 角色与分派

| 角色 | 逻辑标识 | 职责 | 只读级别 |
| --- | --- | --- | --- |
| 需求分析 Agent | `fr-requirements` | 需求基线、验收条件、可行性、微范围与红线核查 | 强制只读 |
| 设计作者 Agent | `fr-designer` | 技术设计、自查、返工答复 | 不适用 |
| 设计 Reviewer Agent | `fr-design-reviewer` | 设计独立评审与复审 | 强制只读 |
| 开发 Agent | `fr-developer` | 实现、修复、白盒自测、diff 自查、影响面说明、黑盒 UT 执行与复测 | 不适用 |
| 代码 Reviewer Agent | `fr-code-reviewer` | 代码独立审查、复审、影响面核验 | 强制只读 |
| 用例作者 Agent | `fr-test-case-author` | 正式用例、覆盖映射、自查、返工答复 | 不适用 |
| 用例 Reviewer Agent | `fr-test-case-reviewer` | 用例独立评审与复审 | 强制只读 |

- 各专业角色使用彼此不同的独立上下文，且独立于主 Agent。
- 首次分派即给出完整任务、版本化输入、权限、交付物和完成条件。
- 角色子 Agent 直接履约，禁止再次委派；主 Agent 负责追加分派。
- 分派和返工遵循 [子 Agent 分派与交接](references/subagent-dispatch.md)。
- 只读角色默认使用 `enforced`；降级核验仅在报告缺口并获用户明确批准后执行。
- 可核对的外部人工身份也可作为角色证据，不虚构 Agent 会话。
- QA 在研发交接后由实际 QA 人员承担，研发交付不等于 QA 通过。

## 主流程

每步先固定输入版本，取得角色实际产物并核对，再按下表推进。

| 阶段 | 输入与动作 | 完成条件 |
| --- | --- | --- |
| 1. 需求与可行性 | PRD、项目约定、必要代码 → 需求分析只读取证 | 验收条件有来源，关键歧义已消除或明确阻塞 |
| 2. 设计（仅 `standard`） | 已确认基线 → 调用 `xu-design-review-loop` | 设计独立评审通过，无未解阻塞 |
| 3. 实现 | 已确认设计或 `lite` 微范围 + 编码授权 → 开发实现 | 固定 `codeSnapshot` 和变更范围，达到送审状态 |
| 4. 白盒验证与代码审查 | 固定快照 → 调用 `xu-dev-review-loop`，明确按已启动的 FR 流程准备 UT 交接 | 白盒自测、diff 自查、独立代码审查均通过 |
| 5–7. 正式用例、黑盒 UT、QA 交接 | 已审快照、白盒与审查证据、原开发角色及用户指定的用例格式 → 按 `xu-dev-ut-loop` 执行 | 用例独立评审、用户确认后由原开发者执行，按当前构建及证据汇总通过、失败、受阻项 |

### 人工门禁

| 门禁 | 必须取得的用户确认 | 未确认时 |
| --- | --- | --- |
| A（`standard`） | 需求基线与可行性 | `WAIT_USER`，不得进入设计 |
| B（`standard`） | 已评审通过的具体设计版本 + 实现授权 | `WAIT_USER`，不得编码 |
| AB（`lite`） | 精简需求基线 + 豁免设计闭环 + 实现授权 | `WAIT_USER`，不得编码 |
| C | 已独立评审通过的当前用例版本 | `WAIT_USER`，不得正式测试 |

预先给出的笼统实现授权不能代替具体设计版本确认。

### 可选预起草

`preDraftCases` 默认关闭。
仅在用户在 B／AB 后显式开启，且宿主支持无争用并行分派时启用。
开发实现期间，`fr-test-case-author` 可基于已确认需求与设计形成 `pre-draft` 骨架。
阶段 4 通过后，原作者须对齐最终快照与回归风险，转为 `formal` 后才可送审。
预起草不得提前触发用例独立评审、门禁 C 或正式执行。

### UT 缺陷回流

按 `xu-dev-ut-loop` 固定版本和本轮用例清单，整轮完成（`fullRoundCompleted: true`）后才发起批量回流，禁止中途转入修复。
批次修复、自验和代码复审交 `xu-dev-review-loop`，复审通过后回到 UT 以已审新快照重建并复测。

## 异常路由

| 触发条件 | 动作 | 终态／去向 |
| --- | --- | --- |
| 需求变化 | 需求分析更新基线，相关角色重估影响并重确认 | 回到最早受影响阶段 |
| 实质设计变化 | 独立设计复审 + 用户重确认，检查实现和用例影响 | 回到阶段 2 |
| 用例实质变化 | 原作者修改、独立复审、用户重确认 | 回到阶段 5 |
| 快照、构建、设备或关键环境变化 | 失效项重审重测，旧结论不得直接继承 | 回到对应受影响阶段 |
| 仅补执行记录或证据 | 核对证据对应版本，不冒充新版本实测 | 可保留原结论 |
| 内环达上限仍未通过、连续两轮阻塞未减或超 20–30 分钟 | 设计、代码、用例轮次和 UT 回流上限按各子技能，汇总本轮阻塞与缺口 | `WAIT_USER`，决定继续、缩范围或人工接手 |

## 离散终态与交付边界

每个步骤只能落入以下一种终态：

| 终态 | 使用条件 | 主 Agent 行为 |
| --- | --- | --- |
| `ADVANCE` | 当前产物、角色隔离、只读证据和通过条件全部满足 | 进入下一阶段，并输出紧凑状态卡 |
| `WAIT_USER` | 等待门禁、编码／修复授权、只读降级批准、超时或熔断决策 | 停下并只询问当前所需决定，附已完成证据与缺口 |
| `BLOCKED` | 角色不可用、隔离碰撞、入口证据缺失、指纹漂移、红线冲突 | 停止推进，报告缺口，不代做或宣布通过 |

日常阶段切换、门禁等待和交接末尾输出 6–8 行紧凑状态卡；
跨会话交接、调用台账校验或用户明确要求时，才输出稀疏 `flow-ledger` JSON。
格式、字段与落盘边界见 [基线与文档元数据](references/requirements-and-stages.md)。

文档默认在对话中呈现，只有用户给出路径并明确授权写入时才落盘。
提交、推送、合入、部署、设备改状态和对外发送交接材料均须分别明确授权。
