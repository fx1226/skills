# xu-fr-flow

用户显式调用本技能时启动完整 FR 流程，调用方式以当前客户端为准。各角色通过相应专业技能执行；缺少必需技能、角色或独立上下文时，报告受影响的阶段及缺口。

## 角色契约

**主 Agent 负责流程计划和调度。** 盘点输入、划定阶段与依赖、固定版本和授权、选择实际能用的子 Agent 工具。根据依赖分派并等待实际产物，核对版本、角色、证据和通过条件，汇总交付及未决事项。技术方案由设计作者制定，具体用例由用例作者设计，专业评审和实测结论由承担该角色的子 Agent 出具。**用户负责 A、B、C 的人工确认、权限授予和是否接受剩余风险。**

以下实质任务分别交给独立子 Agent。每个角色占用一个不同于主 Agent 和其他角色的上下文。逻辑标识用于台账，也可映射到当前 Harness 的角色配置。

| 角色 | 逻辑角色标识 | 职责与交付 |
|---|---|---|
| 需求分析 Agent | `fr-requirements` | 只读提交带来源的需求基线、验收条件、可行性和待确认项 |
| 设计作者 Agent | `fr-designer` | 提交技术设计、自查和逐项返工答复 |
| 设计 Reviewer Agent | `fr-design-reviewer` | 只读给出当前设计版本的独立结论、问题和复审结果 |
| 开发 Agent | `fr-developer` | 实现、修复、构建、自测、diff 自查，提交代码快照及验证证据 |
| 代码 Reviewer Agent | `fr-code-reviewer` | 只读核实快照、改动和验证证据，给出独立审查及复审结论 |
| 用例作者 Agent | `fr-test-case-author` | 提交正式用例、覆盖映射、自查和逐项返工答复 |
| 用例 Reviewer Agent | `fr-test-case-reviewer` | 只读核对用例版本、覆盖、可执行性和选定格式，给出独立结论 |
| 测试执行 Agent | `fr-test-executor` | 按确认用例正式执行，提交实测证据、缺陷复现、复测和 QA 交接材料 |

分派前读 [子 Agent 分派与交接](references/subagent-dispatch.md)，按当前 Harness 的原生工具或已获准的扩展绑定逻辑角色。可用的专用角色配置优先；能新建独立上下文并满足同等范围和权限要求时，可用通用子 Agent 工具显式指定一个逻辑角色。用可核对的上下文身份验收隔离，分别记录上下文标识与运行／续接句柄。

分派任务包含角色、目标、固定输入和证据、允许的操作、交付物和通过条件；首次调用即提交完整任务。收到实际结果并核对当前版本后，才分派有依赖的下游角色。仅对没有前置依赖且不会争用写入路径、设备或共享数据的任务并行。所有分派由主 Agent 负责。角色子 Agent 直接完成本角色工作，禁止再次委派，额外分派需求交回主 Agent。QA 在研发交接之后由实际 QA 人员承担。

## 启动与恢复

先读取用户提供的 PRD/FR、项目文档和必要代码，盘点已有基线、设计、实现、审查、用例及执行记录，以及各角色身份、会话和交接台账。固定需求版本、设计版本、代码快照、用例版本和环境/设备版本；核对材料的来源、评审结论及其适用版本，不能只看文档上的“已完成”。恢复的是角色责任，不因新会话将已有独立结论算作新工作。人工确认以用户明确陈述或可核对的确认记录为准。

从证据支持的**最早未完成或已失效阶段**继续：只有 PRD 从第 1 步开始；已有基线核对 A；已有设计草案进第 2 步，已确认设计核对 B 和实现授权后进第 3 步；已有实现核对第 4 步审查；已有用例核对第 5 步及 C；已有执行记录核对第 6 步；测试返工按版本变化规则退回。缺少前置证据或关键歧义时，列出缺口并等待，不凭状态推定通过。用户已明确说明 PRD 与可行性已确认时记录 A，不为同一确认重复停顿，但仍须指出并解决阻塞性歧义。

需求基线和三份逻辑文档的内容及元数据见 [requirements-and-stages.md](references/requirements-and-stages.md)：建立或核对基线、组织文档或恢复历史状态时读取。默认在对话中输出；只有用户给出保存路径并授权写入时才写项目文档，不自行创建项目文档目录。

## 阶段与门禁

1. **需求与可行性。** 分派需求分析 Agent 只读分析 PRD、项目文档和必要代码，区分明确需求、推断和待确认问题，形成带来源的需求基线、可判定验收条件、约束、风险及可行性预分析。**完成条件**：每项验收条件有来源，关键歧义已解决或列为阻塞，设计可据此判断覆盖。
   - **A 人工确认**：提交基线及可行性供用户确认；有阻塞问题或无有效确认时等待。用户已明确确认 PRD 与可行性可记录继续，但不消除关键歧义。
2. **设计。** A 有效且无需求阻塞后，分派设计作者和设计 Reviewer，通过 `xu-design-review-loop` 完成设计、独立评审及必要复审，交付对应基线和设计版本的结论及未决项。**完成条件**：独立设计评审通过且无阻塞；否则按该技能处理或停止。
   - **B 人工确认**：评审通过仅表示待确认；用户须明确确认已产生且独立评审通过的具体设计版本，并授权实现，才进入编码。设计前概括要求实现或授权修改项目，只记录为实现授权，不构成设计确认；即使同一提示要求设计后直接实现，也须在交付该版本评审结论后等待确认。没有两者则等待。
3. **实现。** B 有效且用户明确授权编码后，分派开发 Agent 按确认的设计实现并保留版本证据。**完成条件**：实现达到送审状态，固定当前代码快照及变更范围。
4. **研发自测和代码审查。** 分派开发 Agent 和代码 Reviewer，通过 `xu-dev-review-loop` 完成研发自测、diff 自查、独立代码审查及必要修复复审。**完成条件**：该技能对当前快照给出独立审查通过且无阻塞；失败或受阻继续处理或停止，不进入第 5 步。此处不额外设置人工门禁。
5. **正式黑盒用例。** 当前代码审查通过后，分派用例作者和用例 Reviewer，通过 `xu-dev-ut-loop` 设计正式黑盒用例并完成独立评审及必要复审。将用户对本次用例指定的 Hillstone／Richsun 格式、模板及载体随任务传递，按该技能的用例格式规则处理。**完成条件**：用例格式符合交付约定，覆盖和评审结论对应当前基线、设计与代码快照，独立评审通过且无阻塞。
   - **C 人工确认**：提交用例及评审结论；用户明确确认当前用例之前，不执行正式测试。
6. **研发测试。** C 有效后分派测试执行 Agent 通过 `xu-dev-ut-loop` 在本地或专用设备执行，核对构建产物、设备软件及环境版本，逐项记录结果和证据。设备刷写等有副作用的操作须有相应授权；缺设备、权限或环境则报告受阻。**完成条件**：必验项在对应版本上均有实际通过证据；失败或受阻不得宣称研发测试完成。发现代码缺陷按下方规则返工。
7. **交付 QA。** 整理版本、覆盖、执行证据、缺陷复测和未决风险，向用户提供研发交接材料；对外发送须另获授权。**完成条件**：可区分已通过、失败和受阻项及其证据，明确研发交付不等于 QA 通过。若有失败或受阻，只能交接当前状态，不能称研发测试完成。

提交、推送、合入和部署均须用户对具体动作另行授权。每次停止或等待时报告当前阶段、对应版本、已完成证据、阻塞项和继续所需的确认或权限。

## 版本变化与退回

以下为本流程退回规则的唯一权威；复用历史结论前先核对其适用版本。

- **需求变化**：分派需求分析 Agent 更新基线，由相应角色重估设计、代码和用例影响；受影响需求与设计重新人工确认，按影响回到相关阶段。
- **实质设计变化**：独立设计复审并人工确认，检查实现和用例影响；实现仍须有授权。
- **代码修复且外部预期不变**：测试执行 Agent 记录并返回缺陷，主 Agent 转交原开发 Agent 修复、自测及 diff 自查，再由原代码 Reviewer 回第 4 步增量复审；按影响面重建后由原测试执行 Agent 在新快照复测失败及受影响项。角色交接遵循角色契约；若外部预期变化，同时适用需求或设计变化规则。
- **用例实质变化**：独立用例复审并重新人工确认，再执行受影响项。
- **仅补测试证据或执行记录**：可保留原结论，但须核对证据对应正确版本，不把补记录当作新版本实测。
- **构建产物、设备软件或关键环境变化**：旧执行结果不得直接继承；重验受影响项。
- **代码快照漂移**：复核漂移及影响；旧审查和测试结论仅适用于原快照，重新审查、测试受影响部分。
